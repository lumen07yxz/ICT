## DEV-2 产品入口与功能边界

| 顶部一级入口 | 形式 | 首版职责 |
|---|---|---|
| 工作台 | 文字 | 项目与论文复现同级；待办、最近运行摘要与快捷操作按真实数据呈现 |
| 模板市场 | 文字 | 受控内置模板列表、搜索、详情、版本及实例化 |
| 仓库 | 图标 | 图标、名称提示、可访问标签、开放状态 |
| Agent 对话 | 文字 | 独立对话、显式上下文引用、工作流草稿、提案与工具记录 |
| 科研支持 | 图标 | 表达云显卡和大模型算力支持，提供名称提示与开放状态 |
| 个人信息与设置 | 文字 | 个人资料、界面偏好、通知、账号安全与服务配置，按实际能力开放 |

工作台“项目”管理研究目标及其工作流和数据；“论文复现”独立管理复现任务。论文复现任务可选关联项目，其生命周期、工作流、运行和报告不依赖项目存在。实验核验作为该模块的任务类型，沿用规则、比较与复核机制。

运行只在具体工作流内发起、查看历史和处理失败；工作台汇总状态并跳转到对应工作流。版本、产物、证据与报告均回到对象上下文，不额外创建顶层中心。模板市场与 Agent 对话各有独立页面。

仓库与科研支持只需入口，不预设仓库采用某种托管方式，不在首版引入算力租赁、计费、配额调度或完整 GPU 云平台。后续接入须另定服务范围和验收条件。

## DEV-3 页面、路由与服务映射

以下为目标路由建议，不要求替换当前路由名称；重点是层级和可追溯的上下文。

| 页面或入口 | 建议前端路径 | 依赖服务 | 核心验收 |
|---|---|---|---|
| 工作台项目列表 | `/workbench/projects` | Project、Activity | 搜索项目并继续所属工作流 |
| 工作台论文复现 | `/workbench/reproductions` | Reproduction | 无项目也可创建、重载复现任务 |
| 项目详情 | `/workbench/projects/:projectId` | Project、Dataset、Workflow | 只展示授权资源，可跳到关联复现任务 |
| 复现任务详情 | `/workbench/reproductions/:taskId` | Reproduction、Evidence、Workflow | 保存论文主张、基准与规则，查看差异和复核 |
| 工作流编辑器 | 在所属项目或复现任务下嵌套 `/workflows/:workflowId` | Registry、Workflow、Run | 修改图真实影响执行；返回保留上下文 |
| 运行详情 | 所属工作流下 `/runs/:runId` | Run、Artifact、Event | 查看该次快照、节点错误、日志和产物 |
| 模板市场与详情 | `/templates`、`/templates/:templateId` | Template | 固定版本复制到已选择的目标容器 |
| Agent 对话 | `/agent`、`/agent/:conversationId` | Conversation、Proposal、AgentAdapter | 独立对话，可显式引用和移除上下文 |
| 个人信息与设置 | `/settings/profile`、`/settings/preferences` 等 | Profile、Settings | 保存后重载仍一致，校验错误可理解 |
| 仓库、科研支持 | 顶部图标，目标后续接入 | EntryStatus | 提示名称与开放状态，不跳到空白假页面 |

建议前端按 `app-shell`、`workbench`、`templates`、`agent`、`settings`、`workflow-editor` 组织职责；后端按 Project、Reproduction、Resource、Template、Workflow、Run、Artifact/Evidence、Conversation/Proposal、Profile/Settings 组织服务。可映射进现有目录，不为命名一致而整体搬迁代码。

## DEV-4 共享数据模型与不变量

| 对象 | 建议关键字段 | 约束 |
|---|---|---|
| Workspace | id、name | 统一隔离边界 |
| Project | id、workspace_id、goal、status | 项目资源的独立容器 |
| ReproductionTask | id、workspace_id、kind、linked_project_id、claim、baseline、criteria_version、status | linked_project_id 可空；论文复现与实验核验共用任务结构 |
| Workflow | id、workspace_id、owner_type、owner_id、current_version | owner_type 为 project 或 reproduction，归属恰有一个 |
| WorkflowVersion / EditorDocument | id、workflow_id、name、description、graph、schema_version、content_hash | 保存工作流名称、说明和可编辑图；版本不可变；节点/边 ID 稳定。旧版本缺少名称/说明时保留为空，恢复时只还原其已有字段 |
| ExecutionPlan | id、workflow_version_id、plan_schema_version、targets、resolved_components、plan_hash | 编译产物不可变；排除纯 UI 布局；运行绑定计划哈希 |
| ComponentDefinition | component_id、version、input_schema、output_schema、execution_target、executor_version、dependencies、permissions、resource_limits、cache_policy | 由受控注册表提供；表单、类型校验和执行器共用同一版本契约 |
| ResourceRef | id、workspace_id、owner、resource_id、resource_version、permission、content_hash、availability、sync_state | 不因项目关联而绕过授权；本机缓存需记录哈希、来源和可用状态 |
| TemplateVersion / TemplateInstance | template_version_id、graph、dependencies、workflow_id、target_owner | 实例固定模板版本和来源；更新不改已有实例 |
| Run / NodeRun | id、workflow_version_id、plan_hash、requested_outputs、execution_target、cache_key、input_snapshot、status、sync_state、timestamps、error | 运行绑定图/计划/输入；节点记录依赖、执行器版本、缓存命中和产物 |
| CacheEntry | signature、component_digest、environment_fingerprint、artifact_refs、created_at、expiry、source_run | 仅缓存满足组件策略的完整产物；所有命中仍检查权限和哈希 |
| Artifact / Evidence | id、run_id、node_run_id、type、uri、checksum、source | 元数据与大型文件分离，访问必须鉴权；缓存只保留产物引用 |
| VerificationResult | task_id、criteria_version、run_ids、comparison、conclusion、reviewer、reviewed_at | 结果需基准、实际运行与规则；运行成功不等于检验通过 |
| Conversation / Proposal | id、workspace_id、context_refs、actor、target_version_hash、criteria_version、status | 对话可无科研对象引用；执行前必须指定合法目标 |
| Profile / Preferences | user_id、display_name、avatar_ref、preferences、revision | 账号安全设置按实际身份服务能力开放 |

`owner_id` 必须有数据库引用完整性约束，不能仅靠前端判断；实现方案见 ENG-13。资源关联、跨容器复制和授权分别处理。归档项目不删除独立复现任务的历史证据；引用失效明确标记，不静默替换为最新资源。

草稿、提案、运行、节点和同步状态分别保存。`WAITING_EXTERNAL` 是节点执行状态，不是网络故障或平台队列状态；运行完成后，本机未同步状态也不得覆盖科研运行结果状态。图修改后原审批不能自动授权新版本。重试、重跑创建新的运行关联，保留原失败记录和已完成产物。

## DEV-5 API 与事件建议契约

本节是开发建议，不是现有接口清单；现有接口满足同一语义时优先复用。所有受保护请求由服务端校验操作者、工作空间、归属及引用权限。

| 接口组 | 建议 HTTP 接口 | 行为 |
|---|---|---|
| 项目 | `GET/POST /api/projects`、`GET/PATCH /api/projects/{id}` | 列表、创建、读取、更新授权项目 |
| 独立复现 | `GET/POST /api/reproductions`、`GET/PATCH /api/reproductions/{id}` | 创建无需 project_id；关联项目显式鉴权 |
| 复核 | `POST /api/reproductions/{id}/reviews` | 固定规则与运行引用，保存结论、依据和操作者 |
| 模板 | `GET /api/templates`、`GET /api/templates/{id}/versions/{version}` | 浏览可用模板和依赖 |
| 实例化 | `POST /api/templates/{id}/instances` | 传 template_version、target_owner、幂等键，返回 workflow_id |
| 工作流 | `POST /api/workflows`、`GET/PATCH /api/workflows/{id}` | 创建需 owner；编辑携带 revision 防覆盖 |
| 校验与版本 | `POST /api/workflows/{id}/validations`、`POST /api/workflows/{id}/versions` | 返回关联节点的问题；保存不可变快照 |
| 提案与审批 | `POST /api/proposals`、`POST /api/proposals/{id}/approve` | 绑定版本哈希、输入及复现任务规则版本；人工批准后再次校验并幂等创建运行 |
| 运行 | `POST /api/workflows/{id}/runs`、`GET /api/workflows/{id}/runs` | 用户直接提交遵循相同审批策略，不绕过策略 |
| 运行详情 | `GET /api/runs/{id}`、`POST /api/runs/{id}/cancel` | 快照、状态与取消；UI 路径仍在工作流内 |
| 日志与产物 | `GET /api/runs/{id}/events`、`GET /api/runs/{id}/artifacts` | 增量事件、日志及授权产物引用 |
| 对话 | `POST /api/conversations`、`POST /api/conversations/{id}/messages` | 显式 context_refs；适配 AgentArts，不把密钥下发前端 |
| 个人中心 | `GET/PATCH /api/me`、`GET/PATCH /api/me/preferences` | 仅操作当前用户；敏感账号变更走身份服务 |

统一错误建议包含 `code`、`message`、`request_id`、`details` 与可定位的 `node_id` 或字段路径；例如版本冲突、无权限、输入缺失、类型不兼容、依赖不可用。用户看到可行动摘要；授权人员可展开技术详情。

本机执行接口由随电脑端安装包启动的受限 loopback runtime 提供；接口只接受有效的 HTTP `127.0.0.1`/`localhost` 来源（允许本机动态端口），签发绑定来源的短期会话凭据，并拒绝非 loopback 来源、网页任意文件路径、命令或执行代码。平台 API 与本机 runtime 分别报告可用性，工作流按节点执行目标选择本机或平台通道。本机图、运行和产物使用本地持久化；联网恢复、登录或后台刷新均不自动上传，只有用户显式发起同步后才将允许的项目元数据与工作流定义加入同步队列；敏感数据、文件、运行、报告、日志与凭据不自动上传。

运行事件包含 event_id、run_id、node_id（如适用）、递增序号、时间与状态。可按现有能力使用轮询、SSE 或 WebSocket；重连从游标继续，重复事件可去重，断连标记为状态暂不可更新，不推测任务成功或失败。状态以持久化记录为准。

日志至少关联 request_id、workspace_id、actor_id、owner、workflow_version_id、run_id、node_id 与执行器版本。记录节点开始/结束、耗时、重试、错误码和受控栈信息；隐藏令牌、敏感数据与原始隐私材料。日志详情与业务摘要通过同一运行关联。

本机执行接口由电脑端安装包启动的受限 loopback runtime 提供。建议以独立 `/runtime/v1` 契约编译并运行本机计划；平台工作流 API 负责平台对象、审批和远端 Worker。两者返回相同的 ExecutionPlan/Run/NodeRun 语义，但分别持久化执行状态。运行事件应新增 `waiting_external`、`cached`、`partially_succeeded` 和同步状态；同步状态不混入运行状态。

比赛版 P0 包含下表十项架构能力，按可演示闭环分批交付，不要求首批一次完成全部执行端：

| P0 能力 | ICT 适配口径 | 比赛交付批次 |
|---|---|---|
| Workflow Compiler | 将 `EditorDocument` 编译为独立、不可变的 `ExecutionPlan`；固定组件版本，校验图、Schema、连线类型、权限、依赖和资源，并计算 `plan_hash` | B1：第一批 |
| 类型化节点 Schema | 由 ICT 版本化组件注册表统一提供端口、参数表单、类型规则、执行目标/绑定、依赖、权限和资源声明 | B1：第一批 |
| 按输出裁剪依赖图 | 以用户选择的报告/指标节点为目标，只编译其祖先闭包；未请求的独立实验分支不运行 | B1：第一批 |
| Ready Queue 与依赖阻塞 | 以依赖计数释放就绪节点；失败只阻断依赖下游，独立分支按策略继续 | B1：第一批 |
| 执行状态机与异步等待 | 区分 `READY / RUNNING / WAITING_EXTERNAL / SUCCEEDED / FAILED / BLOCKED` 等状态；外部等待可以恢复且有持久事件 | B1：第一批 |
| Input Signature 缓存 | 基础键覆盖组件/实现版本、参数、上游 Artifact 哈希、依赖和运行环境；随机种子/模型版本在对应组件需要时纳入；命中仍写本次 `NodeRun` | B3：基础版 |
| ArtifactHandle | 节点间传递有类型、内容哈希、授权状态和来源的产物引用；大文件不进入调度器常驻内存 | B2：支撑 CSV 闭环；后续通用化 |
| 资源请求与准入 | 节点声明 CPU、内存、GPU/显存、时长和输入上限；首版做静态检查、活动运行数限制，超限时拒绝或排队，不做复杂显存调度 | B3：基础版 |
| 本机与平台分离执行 | 按 `local / network / platform` 逐节点路由。本机已缓存且依赖齐全的节点离线可跑；网络节点只访问固定、受控端点；平台节点依赖真实平台 Worker | B3：路由与阻断先完成；真实平台 Worker 需服务可用后验收 |
| 故障隔离 | 分别持久化节点错误、工作流部分失败和 Worker 故障；监督后台任务并在 runtime 重启后恢复/标记未完成运行 | B3：基础监督；独立 Worker 进程池与沙箱后置 |

比赛版工作流优先级按用户确认顺序执行：先交付 B1 前五项执行骨架；随后只接入一个本机 CSV 结构预检组件，形成可演示离线闭环；缓存与资源管理先做到支持该闭环的基础版。ArtifactHandle、授权、运行记录和节点错误状态只实现支撑此闭环所需的最小能力，不扩展成通用分布式产物平台、GPU 调度器或独立 Worker 沙箱。CSV 报告必须标注“结构预检，不是科研结果”。入口与真实持久化、独立复现任务、基础模板市场、同协议画布/Agent 草稿、医学主闭环及基本论文主张对比/人工复核仍属于 P0 交付范围。界面展示未具备的高级能力时要明确不可用；运行校验拒绝不受支持的控制结构。

P1 增加动态条件、受控代码复现、统计复算、子工作流、循环与恢复能力，以及经审核的第三方组件包管理、依赖隔离和更完整的缓存清理策略。P2 扩展学科、协作、模板发布与实际算力/仓库服务。开放工作流的长期表达能力不意味着首版执行器必须支持全部控制结构；不将任意 Python 节点热加载、自动联网安装依赖或显存块交换列为 P0。

ComfyUI 源码采用 ready-node/依赖阻塞模型，支持输出目标、缓存感知依赖、运行时新增依赖与异步阻塞；其 PromptExecutor 逐个 stage 节点，异步节点可重叠，不等于所有独立节点无界并发。ICT 的切片顺序据此调整：先稳定编辑文档与 ExecutionPlan 边界，再交付静态 DAG 和受资源上限的执行器；节点级 lazy input 与运行时图扩展通过版本化接口预留，后续实现。

## DEV-7 开发切片与交付顺序

| 阶段 | 页面交付 | 服务与数据交付 | 退出条件 |
|---|---|---|---|
| 0：入口与归属 | 六个一级入口、工作台两个分支、基础设置和模板目录 | Project、Reproduction、owner 约束、个人资料存储 | 无项目可建复现任务；模板副本归属正确；图标有名称与状态 |
| A：最小画布 | 节点目录、画布、属性、保存与校验 | 注册表、端口、图协议、版本和本机 compiler / 平台服务校验 | 三个测试节点可保存、重载，错误可定位 |
| B1：前五项执行骨架 | 画布选择输出目标、编译/校验结果、节点状态 | Workflow Compiler、类型化 Schema、目标闭包、ready queue/依赖阻塞、异步状态机 | 静态图可编译；目标外分支不运行；错误只阻断依赖下游；外部等待有独立状态 |
| B2：离线 CSV 演示闭环 | 本机文件选择、可选字段筛选/重排、结构报告与运行溯源 | 独立本机 runtime、`ict.data.csv_select_columns`、Run/NodeRun、ICT 现有 `inspect_manifest()`、带来源的 ArtifactHandle 与 SHA-256 | 平台服务和网络关闭时可完成 CSV 源→字段选择→结构预检；逐行处理、不覆盖输入、不保存记录原文；报告明确“结构预检，不是科研结果” |
| B3：基础缓存、执行路由与资源保护 | 缓存命中来源、目标可用性、资源阻断和故障恢复说明 | 单一本机 Input Signature 持久缓存、ArtifactHandle 引用、声明值资源准入、local/network/platform 逐节点路由、输入大小/并发上限、后台任务监督与重启恢复 | 相同确定性输入可复用已校验 ArtifactHandle 且保留新 NodeRun；平台不可用时对应节点阻断而本机分支继续；超过静态资源预算时阻断；任务异常与节点错误可区分 |
| C：医学与基本核验 | 数据质量、双模型对比、独立复现任务比较及报告 | 真实科研节点、预设规则、比较与证据 | 固定授权数据可重跑；基本主张对比有真实运行依据 |
| D：Agent 闭环 | 独立对话、上下文、提案、草稿打开画布 | AgentArts 适配、受控工具、审批幂等与二次校验 | 草稿可编辑并执行；未批准无运行；结果回读可追溯 |
| E：深化与稳定性 | 复核、差异阅读、异常/空态与恢复反馈 | 证据深化、权限/版本冲突处理、部署与复现材料 | UI 与后端状态一致；完整演示可重复，无越权或伪造结果 |

R1 负责研究目标、获准数据、指标、基准、判定规则和科研正确性；R2 负责归属、API、图执行、状态、日志、权限与存储；R3 负责应用外壳、模块页面、画布、AgentArts 配置及集成交互。每个切片由 R2/R3 联调，R1 验收科研内容，教师审核范围与科学结论。

每次开发只推进一个能从页面走通到持久化或真实运行的切片。先盘点当前源码和依赖，再确定改动清单；不要把本文的建议目录、路由或接口宣称为已有实现。技术库版本和外部服务能力在实施时核实与锁定，本次合并不作新的外部产品事实承诺。

## DEV-8 集成验收与 AI 开发任务格式

至少走通四条端到端路径：

1. 项目路径：工作台新建项目 → 模板实例化 → 改参数/连线 → 保存版本 → 在工作流内运行 → 节点日志和产物 → 报告追溯。
2. 独立复现路径：工作台论文复现 → 不关联项目建任务 → 固定主张/实验基准与规则 → 导入数据或引用授权资源 → 编辑工作流 → 运行 → 实际值对比 → 人工复核与报告。
3. Agent 路径：独立对话 → 显式引用目标 → 生成草稿 → 画布修改 → 校验 → 提案获批 → 实际运行 → 回读结果；修改图、规则或输入后原审批失效。
4. 个人中心与入口：一级进入个人资料/偏好 → 合法保存并重载 → 错误值提示；仓库和科研支持图标可聚焦、显示名称和准确开放状态。

异常验收覆盖无权限、跨工作空间引用、资源失效、模板依赖缺失、非法连接、并发编辑冲突、审批过期/版本不符、重复提交、Worker 失败、取消、事件断连及证据不足。按实际改动运行相应测试与人工操作，不用静态页面或预置成功状态代替真实链路。

交给 AI 编程助手的每项任务应包含：目标页面与用户动作、所属项目/复现任务、前置依赖、现有代码位置、允许改动范围、数据与 API 契约、状态及错误、交付物、运行命令和可观察的验收结果。文档内原有开发指令仅作为后续开发任务参考，本次工作不执行代码实现、部署或提交。

# UI-1. 设计摘要

## UI-1.1 当前需要解决的问题

现有设计思路已经包含浅色科研工作台、节点式画布、组件复用、数据管理、工作流内运行、检验模块和 Agent 助手等关键方向，但仍存在一些容易导致软件“看起来不专业、用起来不顺手”的风险：

1. **产品结构偏功能罗列。** 工作台、项目、工作流、组件、运行和检验之间的从属关系还需要进一步定义。
2. **把示例流程误当作固定流程。** 六段式流水线只能作为模板，不能成为所有科研任务的固定结构。
3. **视觉规范缺少可执行参数。** 仅规定“浅灰、白色、蓝色、留白”不足以指导前端统一实现，还需要间距、字号、圆角、边框、按钮、表格和状态等设计令牌。
4. **节点画布与常规业务页面之间缺少一致性。** 画布、项目数据、运行详情、检验任务和 Agent 对话可能像不同产品拼接在一起。
5. **编辑、运行和结果查看存在割裂风险。** 用户应该能够从节点配置直接查看运行状态和产物，而不是反复跳转。
6. **缺少完整状态和异常交互规范。** 加载、空状态、校验失败、权限不足、运行中断、数据缺失等情形必须有明确反馈。
7. **功能范围存在优先级混淆。** 比赛交付、后续扩展和长期商业化功能需要分开，避免导航过多、核心流程被稀释。
8. **缺少明确的视觉验收标准。** “好看”必须落实为页面密度、层级、对齐、交互一致性和任务完成效率等可检查指标。

## UI-1.2 设计目标

平台应呈现为一个专业的科研生产力工具，而不是传统管理后台、聊天机器人和节点编辑器的简单拼接。

用户打开软件后，应当能够快速回答以下问题：

- 我现在在哪个科研项目中？
- 当前项目有哪些数据、工作流、运行任务和检验结果？
- 下一步最合理的操作是什么？
- 当前工作流是否可以运行？
- 任务运行到了哪里，失败的原因是什么？
- 检验结论来自哪个数据版本、工作流版本和运行记录？
- Agent 做了什么，哪些建议尚未执行，哪些操作需要我批准？

## UI-1.3 产品体验定位

建议采用三种产品体验的组合，但不直接复制任何单一产品的页面：

- **专业协作工作台：** 清晰的导航、克制的颜色、统一的页面布局和稳定的操作位置。
- **节点式创作环境：** 可自由组合节点、分支、并行任务、条件判断和子工作流。
- **科研检验工作区：** 围绕论文复现与实验核验，关联数据、图表、证据、运行记录和报告。

视觉关键词：**专业、克制、清晰、可靠、可追溯、可扩展。**

# UI-2. 产品信息架构

## UI-2.1 先统一核心概念

产品中以下概念必须明确区分，并在界面中保持一致。

| 概念 | 标准定义 | 用户主要操作 |
|---|---|---|
| 工作空间 | 用户或团队的顶层工作环境 | 切换工作空间、管理成员和权限 |
| 项目 | 围绕一个研究目标组织资源的容器 | 创建项目、查看概览、配置项目资源 |
| 工作流 | 由节点、连接、控制逻辑和参数组成的可执行研究图 | 创建、编辑、校验、版本管理 |
| 节点 / 组件 | 可以在工作流中执行的最小功能单元 | 搜索、添加、配置、运行、复用 |
| 模板 | 可复制并修改的工作流初始结构 | 预览、创建副本、应用到项目或复现任务 |
| 数据集 | 具有版本和元数据的数据资源 | 上传、检查、版本管理、引用 |
| 运行 | 某一工作流版本的一次实际执行实例 | 启动、监控、取消、排错、重跑 |
| 产物 | 节点或运行生成的数据、图表、模型、日志和报告 | 预览、下载、比较、追溯 |
| 证据 | 支持研究主张或结论的来源、数据和分析记录 | 关联、核查、引用、导出 |
| 论文复现任务 | 从工作台论文复现模块建立的独立任务，可关联项目，包含论文主张复现与实验结果核验 | 指定基准与判定规则、配置工作流、执行、比较、复核 |
| 检验结论 | 基于检验任务、实际运行结果和判定规则形成的状态及差异说明 | 查看依据、复核、导出 |
| Agent 提案 | Agent 对工作流、参数或后续研究操作提出的待审核变更 | 查看差异、修改、批准或拒绝 |

不要在不同页面把同一个对象随意称为“模块”“插件”“组件”或“工具”。建议采用以下命名：

- **节点：** 工作流画布上的实例。
- **组件：** 可被添加到工作流的能力定义。
- **模板：** 预先组织好的工作流。
- **工作流：** 用户正在编辑或保存的研究图。
- **运行：** 工作流某一版本的执行实例。
- **产物：** 运行生成的文件或结构化结果。

## UI-2.2 全局导航建议

桌面端采用“顶部一级导航与图标入口 + 当前模块内部导航 + 主内容区”的结构。一级导航包含工作台、模板市场、Agent 对话、个人信息与设置；仓库和科研支持以图标形式放在同一顶部栏。工作流编辑器进入专用的沉浸式工作区，保留所属项目或论文复现任务的上下文和返回入口。

### 建议导航结构

| 顶部入口 | 展示形式 | 职责与内部结构 |
|---|---|---|
| 工作台 | 文字导航 | 内部以“项目”“论文复现”两个同级入口组织日常任务，辅以待办、最近运行摘要和快捷操作 |
| 模板市场 | 文字导航 | 浏览、搜索与预览可复用工作流模板，使用时选择目标项目或论文复现任务 |
| 仓库 | 图标入口 | 顶部保留仓库图标，本版只规定入口位置与名称，不展开仓库业务页面 |
| Agent 对话 | 文字导航 | 独立对话页面，支持研究讨论、上下文引用、工作流提案与执行记录 |
| 科研支持 | 图标入口 | 顶部保留科研支持图标，表达平台提供云显卡算力或大模型算力支持；本版不展开算力管理页面 |
| 个人信息与设置 | 文字导航 | 独立一级页面，按常见软件组织个人资料、偏好设置、通知、账号安全等内容 |

工作台内部结构：

- **项目：** 项目列表 → 项目概览 → 工作流、数据、项目成员与设置；具体工作流内配置组件、管理版本、提交运行和查看历史。
- **论文复现：** 复现任务列表 → 论文依据与复现目标 → 数据和工作流 → 对比、核验、报告与溯源。可独立创建任务，也可关联已有项目；不要求先创建项目。
- **辅助信息：** 待审批提案、失败运行、待复核事项和快捷操作按实际情况补充，点击后定位到具体项目或复现任务。

个人信息与设置保留独立一级导航，头像提供快捷入口；工作空间管理从工作空间切换器进入。项目和论文复现的内部导航随当前对象显示，不与顶部一级入口混排。

**运行不占用独立导航。** 在具体工作流中发起、监控、取消、重试和查看历史；工作台及项目概览仅汇总需要关注的运行，并提供跳转。

**仓库与科研支持按本方案保留顶部图标。** 鼠标悬停和键盘聚焦时显示名称，并提供可访问标签；尚未接入功能时明确提示“暂未开放”。公开社区、计费等扩展按实际产品阶段开放，不能用空页面伪装已实现。

## UI-2.3 全局栏规范

顶部全局栏由一级入口和辅助控件组成：

- 工作台、模板市场、Agent 对话、个人信息与设置四个文字入口，以及仓库、科研支持两个图标入口；当前模块有清晰选中态。
- 当前工作空间 / 团队切换。
- 当前项目或论文复现任务的上下文与切换入口（进入相应对象后显示）。
- 全局搜索。
- 待处理数量；点击后展开工作台待办，并能跳到对应项目、工作流或检验任务。
- 帮助与快捷键。
- 用户头像与设置。

不建议将所有业务操作都堆到顶部。页面级操作应放在对应页面标题区或对象附近。

## UI-2.4 项目内导航

进入项目后，显示项目名称、项目类型、最近更新时间和项目内导航。

建议项目内二级导航：

- 概览
- 工作流
- 数据
- 项目设置

论文复现是工作台内与项目并列的模块，不列入项目内导航。项目概览可以展示已关联的复现任务并跳转；运行记录附属于工作流，报告与证据附属于复现任务或具体运行。

## UI-2.5 关键对象关系

推荐使用以下关系组织产品：

工作空间中的工作台有两个并列分支：项目 → 项目工作流；论文复现 → 复现任务 → 复现工作流。两类工作流均通过“工作流版本 → 运行实例 → 节点运行 → 产物”执行与追溯。复现任务引用论文依据或实验基准，形成检验结论，并可通过关联关系引用项目资源。

模板市场是独立一级模块，模板与组件可被多个项目或复现任务引用。Agent 对话是独立一级页面，可关联项目、复现任务、工作流版本或运行结果；提案执行仍需权限与版本校验。

# UI-3. 全局视觉设计系统

## UI-3.1 视觉原则

1. **内容优先：** 让研究数据、图表、节点和结果成为视觉焦点。
2. **中性色为主：** 页面大面积使用白色和浅灰，品牌色只用于关键操作和选中状态。
3. **层级靠排版建立：** 优先使用字号、间距和轻量底色，不用大量阴影和粗分割线。
4. **一致性优先于装饰：** 同一类型的按钮、卡片、状态和面板必须在全平台保持一致。
5. **密度可控：** 科研数据页面可以信息密集，但要有明确分组；画布区域则应尽量减少无关装饰。
6. **状态可辨识：** 不能只用颜色区分状态，必须同时提供文字或图标。
7. **动效有目的：** 只用于反馈、状态变化和空间关系，不做无意义的持续动画。

## UI-3.2 色彩令牌

建议以中性色为底，使用单一主品牌蓝。具体色值可在品牌确认后微调，但必须通过统一设计令牌管理，不能由各页面自由选择。

| 令牌 | 建议值 | 用途 |
|---|---|---|
| `color-brand-600` | `#2563EB` | 主按钮、主要链接、当前选中 |
| `color-brand-50` | `#EFF6FF` | 选中项浅底色、轻提示背景 |
| `color-text-primary` | `#1F2937` | 页面标题、重要文本 |
| `color-text-secondary` | `#4B5563` | 正文、说明 |
| `color-text-muted` | `#6B7280` | 辅助信息、时间、次要元数据 |
| `color-border` | `#E5E7EB` | 轻边框、表格边界 |
| `color-border-strong` | `#D1D5DB` | 输入框或重点边界 |
| `color-surface` | `#FFFFFF` | 主内容面板、卡片 |
| `color-canvas` | `#F8FAFC` | 页面背景、画布外围 |
| `color-sidebar` | `#F9FAFB` | 侧边栏背景 |
| `color-success` | `#15803D` | 成功状态 |
| `color-success-bg` | `#F0FDF4` | 成功状态浅底 |
| `color-warning` | `#B45309` | 警告状态 |
| `color-warning-bg` | `#FFFBEB` | 警告状态浅底 |
| `color-danger` | `#B91C1C` | 失败、阻断、危险操作 |
| `color-danger-bg` | `#FEF2F2` | 失败状态浅底 |
| `color-info` | `#1D4ED8` | 运行中、信息提示 |
| `color-info-bg` | `#EFF6FF` | 运行状态浅底 |

规则：

- 不要在同一页面同时使用多个互相竞争的主色。
- 成功、警告、失败颜色只用于状态和相关操作，不作为普通装饰色。
- 低对比度浅灰不能用于关键正文或重要按钮文字。
- 颜色方案必须兼顾投影显示和常见色觉差异。

## UI-3.3 字体与字号

优先使用系统无衬线字体，保证中英文混排稳定。中文界面可采用系统默认中文字体栈。

建议字号体系：

| 令牌 | 字号 | 用途 |
|---|---:|---|
| `font-page-title` | 24 px | 页面主标题 |
| `font-section-title` | 18 px | 页面区块标题 |
| `font-subtitle` | 16 px | 卡片标题、面板标题 |
| `font-body` | 14 px | 默认正文、表格内容 |
| `font-secondary` | 13 px | 辅助说明、次要元数据 |
| `font-caption` | 12 px | 标签、时间、简短注释 |
| `font-metric` | 28–32 px | 仪表盘关键指标 |

规范：

- 正文默认使用 14 px，不要把整个平台做成过小的后台字。
- 页面标题与区块标题应有明确层级，但不宜使用过多大字号。
- 表格数值、运行 ID 和版本号建议使用等宽数字或适合对齐的数字样式。
- 关键数据应突出，但不需要每个数字都做成大号指标卡。

## UI-3.4 间距与布局

采用 4 px 基础间距单位，常用值为 4、8、12、16、20、24、32、40 px。

| 场景 | 建议值 |
|---|---|
| 图标与文字间距 | 8 px |
| 表单字段垂直间距 | 16–20 px |
| 卡片内边距 | 16–20 px |
| 页面主区块间距 | 24–32 px |
| 页面左右边距 | 24–32 px |
| 侧栏与主内容间距 | 0–24 px，按布局决定 |
| 画布节点内部间距 | 8–12 px |

避免以下问题：

- 所有内容都挤在屏幕边缘。
- 卡片内部留白过大，导致一屏有效信息过少。
- 每个区块都套一层卡片，形成“卡片套卡片”。
- 页面左右边距、标题位置和筛选栏在不同页面不一致。

## UI-3.5 圆角、边框与阴影

| 元素 | 建议规范 |
|---|---|
| 小控件 | 6 px 圆角 |
| 按钮、输入框 | 6–8 px 圆角 |
| 普通卡片 | 8–10 px 圆角 |
| 大型弹窗 | 12 px 圆角 |
| 普通边框 | 1 px 中性灰 |
| 默认阴影 | 无或极轻 |
| 弹窗阴影 | 清晰但克制 |
| 悬停反馈 | 浅底色或边框变化，必要时轻微阴影 |

避免大量胶囊形按钮、超大圆角卡片、强渐变背景、玻璃拟态、3D 图标和过度阴影。平台的专业感应来自清晰的结构，而不是装饰。

## UI-3.6 图标规范

- 全平台使用同一套图标库和线性风格。
- 图标常规尺寸为 16 px，导航图标可为 18 px，关键空状态插画另行处理。
- 图标必须与文字标签搭配，避免只靠图标猜功能。
- 同一个动作不能在不同页面使用不同图标。
- 不建议使用大量彩色 Emoji 作为正式功能图标。

# UI-4. 界面组件设计规范

## UI-4.1 按钮体系

按钮按动作重要性分为四类：

### 主按钮

适用于页面中最重要、最明确的动作，例如“保存工作流”“提交运行”“批准执行”。

- 同一视觉区域原则上只有一个主按钮。
- 主按钮文案应使用明确动词。
- 运行前校验失败时，主按钮应禁用或转为“查看阻断项”，不能让用户点击后才发现无法运行。

### 次按钮

适用于“取消”“预览”“导出”“添加节点”等次级操作。

- 使用描边或中性底色。
- 不应与主按钮争夺视觉焦点。

### 文字按钮

适用于“查看详情”“展开”“重试”“复制 ID”等轻量操作。

- 不要将危险操作伪装成普通文字操作。
- 低频动作可以放入更多菜单。

### 危险按钮

适用于删除数据集、终止运行、移除成员等有破坏性或不可逆的操作。

- 使用危险色。
- 必要时要求二次确认。
- 确认弹窗应说明具体影响，不能只写“确定吗？”

## UI-4.2 输入控件

所有输入控件应有：

- 明确标签。
- 必要时提供单位、范围或示例。
- 清晰的默认值和必填标识。
- 即时校验和可读错误信息。
- 合理的帮助说明。
- 键盘焦点状态。

数值输入应明确单位；阈值、批次大小、学习率等参数不能只显示一个没有语义的数字。

## UI-4.3 卡片

卡片只用于具有独立语义的内容单元，例如项目、组件、模板、数据集、待审批提案。

标准卡片结构：

1. 标题与必要图标。
2. 一句说明或关键元数据。
3. 状态或分类标签。
4. 主要动作。
5. 次级操作（必要时放入更多菜单）。

不要为每一个小段文字创建独立卡片。列表型内容优先使用表格或紧凑列表。

## UI-4.4 表格

适用于数据集、运行记录、产物、证据和组件版本等需要比较或批量浏览的内容。

规范：

- 表头简短明确。
- 重要列靠左，状态和操作列位置稳定。
- 时间、版本、运行 ID 等次要信息使用辅助文字。
- 支持排序、筛选、分页和空状态。
- 长文本截断并提供查看完整内容的方式。
- 行内展开仅展示摘要，完整内容进入详情面板。
- 操作列不应塞入过多按钮，低频操作进入更多菜单。

## UI-4.5 标签与状态

所有状态使用“文字 + 颜色”，必要时加图标。

| 状态 | 推荐标签 | 说明 |
|---|---|---|
| 成功 | 成功 | 绿色 |
| 运行中 | 运行中 | 蓝色，可配合进度 |
| 排队中 | 排队中 | 中性色或蓝色弱提示 |
| 警告 | 警告 | 黄色 / 琥珀色 |
| 阻断 | 阻断 | 红色，表示无法继续 |
| 失败 | 失败 | 红色 |
| 已取消 | 已取消 | 中性灰 |
| 等待审批 | 待审批 | 琥珀色或蓝色弱提示 |
| 等待输入 | 等待输入 | 中性色 |
| 草稿 | 草稿 | 中性灰 |

状态必须来自后端真实状态，不能由前端根据页面猜测。

## UI-4.6 提示、抽屉与弹窗

- **Toast：** 只用于短暂结果，如保存成功、复制成功。
- **Inline Alert：** 用于当前页面内持续存在的警告或阻断。
- **Popover：** 用于短小的上下文说明。
- **Drawer：** 用于查看节点运行详情、产物元数据和轻量编辑。
- **Modal：** 用于重要确认、复杂表单或必须中断当前操作的决策。

不要用弹窗承载完整的复杂工作区，也不要在普通提示中堆砌大量原始日志。

# UI-5. 页面框架与响应式策略

## UI-5.1 桌面端优先

该产品的节点编辑、图表分析和数据表格主要面向桌面端。建议以 1440 × 900 为主要设计基准，同时验证 1280 × 720 和更宽的桌面屏幕。

- 1440 px：完整三栏工作流编辑器。
- 1280 px：允许收窄左右面板，画布保持优先。
- 较窄窗口：可折叠组件栏和属性栏，不应压缩节点到不可操作。
- 移动端：以项目概览、具体工作流运行状态和检验报告查看为主；复杂画布编辑不应强行缩成三栏。

## UI-5.2 常规业务页面的统一骨架

页面建议统一使用：

1. 页面标题区：标题、说明、主操作。
2. 筛选或工具栏：搜索、筛选、视图切换。
3. 主内容区：表格、卡片、图表或详情。
4. 分页或底部状态（需要时）。
5. 全局反馈层：提示、弹窗、抽屉。

页面标题、工具栏和主内容的间距应在全站保持一致。

## UI-5.3 工作流编辑器的专用骨架

工作流编辑器是产品的核心专业界面，建议采用专用全屏工作区：

- **顶部编辑栏：** 返回所属项目或复现任务、工作流名称、保存状态、版本、撤销/重做、校验、运行。
- **左侧组件面板：** 搜索、分类、组件条目、最近使用。
- **中央画布：** 节点、连线、分组、缩放、迷你地图、自动布局。
- **右侧属性面板：** 当前选中节点的参数、输入输出、说明、运行信息。
- **底部或可折叠运行面板：** 校验结果、运行日志、任务队列、产物摘要。

左右面板应可折叠，中央画布在默认状态下拥有最大空间。不要让常驻聊天窗口挤占画布主体区域。

## UI-5.4 页面层级原则

- 工作台及项目内浏览页使用统一框架；进入项目后保持项目名称和返回工作台入口可见。
- 工作流编辑页使用沉浸式编辑框架。
- 工作流内的运行详情使用“流程 / 结果 / 日志”三类信息的清晰分区。
- 检验报告页使用阅读型布局，不套用编辑器布局。
- 重要操作尽量在当前对象附近完成，减少无意义跳转。

# UI-6. 工作台与项目页面

## UI-6.1 工作台首页

目标：让用户从“项目”或“论文复现”两个同级入口恢复工作，待办和快捷操作辅助定位具体任务。

推荐布局：

### 顶部欢迎与快捷操作

显示简短欢迎语、当前工作空间和主要操作：

- 新建项目
- 新建论文复现任务
- 继续最近项目、复现任务或工作流
- 进入模板市场或 Agent 对话

不要使用大面积装饰性 Banner。欢迎区应简洁，不占用大量首屏空间。

### 主内容区

主内容以“项目 / 论文复现”两个同级标签或分区组织：

- 项目列表，支持最近使用、搜索和筛选；项目卡片展示名称、目标、最近活跃及需要关注的状态。
- 论文复现任务列表，支持新建、继续复现、查看差异和复核；无需先进入项目。
- 最近打开的工作流归属对应项目或复现任务，提供继续工作入口。

右侧辅助栏：

- 跨项目与复现任务的待处理事项：待审批提案、失败或等待人工处理的运行、待复核的检验任务。
- 最近运行摘要，点击后进入所属项目或复现任务的具体工作流与该次运行。
- 根据当前标签、权限和可用能力显示快捷操作，例如新建项目、新建复现任务、使用模板或导入数据。

如果没有待处理事项，不要显示空白大卡片；应折叠该区域或展示简短的空状态。

## UI-6.2 项目列表页

每个项目展示：

- 项目名称。
- 研究领域或项目类型。
- 一句话目标。
- 最近更新时间。
- 工作流数量、数据集数量或最近运行状态等少量关键指标。
- 更多菜单：重命名、复制、归档、删除。

项目列表属于工作台主内容，不另设全局“项目中心”。支持卡片与表格视图切换；项目数量多时，默认表格或紧凑列表更高效。

## UI-6.3 项目概览页

项目标题区显示项目名称、描述、成员或权限信息，以及项目级操作。

主区域建议按“当前进展—工作流—数据—检验”组织：

- 项目工作流列表、最近版本与继续编辑入口。
- 数据集及质量状态。
- 各工作流最近运行的状态、失败任务和跳转入口。
- 已关联的论文复现任务、核验结论与需要复核的差异；跳转到工作台论文复现模块中的对应任务。
- 待审批事项。

不要把所有数据都做成同等大小的统计卡片。优先突出需要用户采取行动的信息。

## UI-6.4 新项目空状态

新项目应提供清晰的起步路径：

1. 说明研究目标。
2. 导入数据或选择已有数据。
3. 选择模板，或进入自由画布。
4. 在该工作流内校验并运行。
5. 查看产物；需要复现论文或核验实验时，从工作台论文复现模块建立任务，并按需关联当前项目与运行。

这只是帮助新手启动的引导路径，不是所有研究任务都必须遵循的固定流程。

# UI-7. 工作流编辑器：核心 UI 规范

## UI-7.1 双模式设计

### 引导模式

面向刚接触节点工作流的用户。

- 从模板开始。
- 以步骤或任务清单解释主要节点。
- 隐藏不必要的高级参数。
- 提供可选的默认配置。
- 用户仍然可以打开画布查看结构。

### 自由画布模式

面向熟悉科研流程的用户。

- 自由添加和连接节点。
- 支持多分支、并行、条件、汇合和子工作流（以实际实现能力为准）。
- 支持节点分组、复制、粘贴、对齐和自动布局。
- 显示端口类型与连接校验。
- 支持保存草稿和工作流版本。

两种模式必须操作同一份工作流定义，不得分别维护两套流程数据。

## UI-7.2 不把六段式作为固定流程

六段式科研流程只作为一个可选示例模板。不同科研任务可能只有几个节点，也可能需要多路数据、多模型并行、循环优化、条件判断、人工审批和嵌套子工作流。

界面应提供以下能力：

- 从空白画布开始。
- 从模板开始。
- 在现有工作流中增加任意节点。
- 添加分支与汇合。
- 将一组节点封装成子工作流。
- 保存当前工作流为模板。

模板负责降低门槛，不能限制自由组合能力。

## UI-7.3 顶部编辑栏

左侧：

- 返回所属项目或论文复现任务。
- 工作流名称。
- 当前项目或论文复现任务路径及面包屑。

中间：

- 保存状态（已保存 / 保存中 / 有未保存更改）。
- 当前版本及执行计划版本。
- 撤销 / 重做。

右侧：

- 校验并编译工作流。
- 运行配置：请求的输出节点、执行目标、资源限制和可用组件。
- 提交运行（主按钮）。
- 更多菜单（导入、导出、版本历史等）。

“运行”按钮分别根据本机 runtime、外部网络/凭据和平台服务判断。纯本地工作流不得因平台 API 不可用而禁用；目标输出依赖的节点有阻断时，展示受影响范围和仍可执行的独立分支。

## UI-7.4 左侧组件面板

包含：

- 搜索框。
- 最近使用。
- 收藏。
- 按类别筛选。
- 组件条目。

建议类别：

- 数据输入。
- 数据处理。
- 文献与证据。
- 统计分析。
- 模型训练。
- 模型推理。
- 评价与比较。
- 控制与调度。
- Agent。
- 可视化。
- 导出与报告。

每个组件条目显示名称、简短说明和必要的兼容性信息。不要在列表里放过多技术参数；完整说明进入组件详情或添加后的属性面板。

## UI-7.5 中央画布

画布应以节点关系为视觉主体。

节点规范：

- 顶部显示节点名称与状态。
- 主体显示最必要的参数摘要。
- 输入和输出端口清楚区分。
- 端口旁显示简短类型提示。
- 运行中、成功、失败、阻断和缓存命中状态必须清晰可见。
- 执行目标与必要依赖应有简短标记，不将“平台服务断连”显示成所有节点的统一错误。
- 选中状态以边框或轻量底色表达，不要使用强烈发光。
- 错误节点旁提供可点击的错误摘要。

画布工具：

- 缩放、适配画布。
- 撤销、重做。
- 自动布局。
- 迷你地图。
- 多选与分组。
- 复制、粘贴。
- 删除和快捷键提示。
- 导入 / 导出工作流（按权限与实现阶段开放）。

节点连接规则：

- 只有兼容端口才能建立有效连接。
- 不兼容连接要即时提示原因。
- 数据连接与控制依赖在视觉上需要有所区别。
- 线条不应遮挡节点标题和关键参数。
- 多分支工作流应有清楚的空间布局，避免线条交叉导致难以理解。

## UI-7.6 右侧属性面板

未选择节点时，显示工作流概要、校验状态和运行配置。

选中节点时，按以下顺序组织：

1. 节点名称与执行状态。
2. 简短用途说明。
3. 输入数据和上游连接。
4. 参数配置。
5. 输出定义。
6. 资源与执行设置（高级项）。
7. 最近一次运行结果。
8. 节点版本与帮助信息。

参数较多时使用分组或折叠面板，不要把所有参数一次性铺满。关键参数要有单位、范围、默认值和说明。

## UI-7.7 底部运行面板

建议使用可折叠的底部区域，作为当前工作流的运行入口和监控区，提供：

- 编译/校验结果与每个执行目标的依赖就绪状态。
- 当前运行、该工作流队列及运行历史；支持排队中、运行中、等待外部、成功、部分完成、失败、已取消筛选。
- 节点状态、缓存命中来源、异步等待、资源占用和错误摘要。
- 产物列表及本机/平台来源。
- 本机未同步、同步冲突和恢复操作。

运行面板默认保持收起或较低高度；失败或等待外部输入时可展开关联详情。平台服务状态不能替代本机 runtime 状态。

## UI-7.8 工作流状态

工作流编辑、提案审批、运行、节点和同步状态分别保存；界面可组合展示，但不能将草稿或缓存命中伪装成新的科研运行结果。

运行状态示例：草稿、校验通过、待审批、排队中、运行中、等待外部、成功、部分完成、失败、已取消。

节点状态示例：待运行、就绪、运行中、等待外部、缓存命中、成功、失败、阻断、跳过。

同步状态单独显示：仅本机、待同步、已同步、冲突。节点与运行状态必须来自本机 runtime 或平台 Worker 的持久记录。

## UI-7.9 运行前校验

校验分为阻断、警告和提示。每条问题包含关联节点、原因、影响和建议操作，点击后定位到画布节点。

编译/校验须核对 ExecutionPlan 版本、目标输出闭包、端口类型、组件与执行器版本、依赖安装、权限、数据和模型缓存、网络凭据、平台能力及资源可行性。平台 API 仅阻断依赖平台的节点和其下游；纯本地分支保持可运行。执行器在运行前还要复核权限、资源和输入快照。

# UI-8. 模板市场与工作流组件

## UI-8.1 组件选择面板

组件选择面板从当前工作流编辑器打开，目标是帮助用户发现和复用科研能力，而不是做成纯展示型商城。

顶部提供搜索和类别筛选，主体提供组件列表或卡片视图。每项组件展示：

- 名称。
- 一句话功能描述。
- 类别。
- 版本。
- 输入输出摘要。
- 是否已安装 / 可用。
- 加入当前工作流的操作；不以“添加到项目”代替创建节点。

评分、下载量、作者社区等信息仅在真实存在相应数据和社区机制后展示。

## UI-8.2 组件详情

组件详情在编辑器内以侧栏或抽屉呈现，建议包含：

- 功能说明。
- 适用场景。
- 输入端口和数据类型。
- 输出端口和数据类型。
- 参数说明。
- 依赖与运行环境。
- 版本历史。
- 使用示例。
- 权限和资源要求。

关键操作是“添加到工作流”或“创建副本”，而不是让用户阅读大量介绍后仍不知道怎么使用。

## UI-8.3 模板选择

模板市场具有独立一级导航，可直接浏览、搜索、筛选、收藏和预览模板。项目或论文复现任务内的“从模板创建”打开同一模板目录并带入目标上下文。模板卡片展示：

- 模板名称。
- 适用研究任务。
- 工作流缩略图。
- 主要节点数量或核心能力。
- 必需数据与依赖。
- 最近更新时间和版本。

模板详情应允许用户预览流程结构，并明确标注需要用户提供的数据、模型或凭据。

点击“使用模板”后选择目标项目或论文复现任务；已有上下文时默认带入并允许核对。应用模板时创建可编辑工作流副本，保留模板来源和版本。尚未选择目标时先完成目标选择，不静默创建项目或跨对象写入。

# UI-9. 项目数据管理与质量报告

## UI-9.1 数据集列表

顶部区域：

- 页面标题和上传操作。
- 搜索框。
- 类型、来源、质量状态、更新时间筛选。
- 卡片 / 表格切换。

表格建议列：

- 数据集名称。
- 类型与格式。
- 样本量。
- 当前版本。
- 质量状态。
- 更新时间。
- 引用项目或工作流数量（有真实数据时）。
- 操作。

不要把所有字段都放进表格。低频元数据进入详情页。

## UI-9.2 上传与本机导入流程

区分“导入到本机受控资源库”与“上传到平台资源库”，不能把本地选择暗示成云端上传：

1. 选择本地文件或已授权数据源。
2. 选择本机保留或显式上传目标，登记来源、许可/授权状态和用途。
3. 检查格式、计算内容哈希并记录文件版本。
4. 执行基础结构预检并说明未检查范围。
5. 展示导入/上传状态和质量问题。
6. 确认创建不可变数据版本。

本机导入不自动上传。离线时只写入本机资源库和同步队列；用户显式发起并通过权限检查后才上传。导入失败与结构预检未通过必须分开表达。

## UI-9.3 数据集详情

详情页采用顶部摘要 + Tab：

- 概览。
- 文件与样本。
- 版本历史。
- 质量报告。
- 使用记录。
- 元数据。

版本信息必须清楚展示。工作流引用数据时，应显示引用的具体版本，而不是默认静默使用“最新版本”。

## UI-9.4 数据质量报告

采用“结论总览 → 分维度分析 → 明细记录”的结构。

顶部摘要：

- 检查状态。
- 总检查项。
- 通过项。
- 警告项。
- 阻断项。

中间图表：

- 缺失值。
- 标签分布。
- 重复样本。
- 数据格式异常。
- 训练 / 验证 / 测试拆分检查。
- 根据任务类型提供的专属质量指标。

底部明细：

- 检查项。
- 检查规则。
- 实际结果。
- 状态。
- 影响。
- 建议操作。

每份报告应标明数据集版本、规则版本、执行时间和运行来源。图表不能脱离数据版本和方法说明单独存在。

# UI-10. 工作流内运行与运行详情

## UI-10.1 工作流运行区

运行区位于具体工作流的编辑器和详情页中。用户选择目标输出、编译计划、检查依赖并提交运行；纯本机运行由本机 runtime 执行，不等待服务器队列。运行历史展示 ExecutionPlan 哈希和目标，说明这次只计算了哪些输出。

运行状态至少区分排队、运行、等待外部、成功、部分完成、失败和取消；节点详情显示依赖阻断、缓存命中、异步等待、资源消耗、错误及产物来源。异步网络请求不应伪装成 CPU/GPU 并行计算。

## UI-10.2 工作流运行历史字段

建议列：

- 运行名称 / Run ID。
- 当前项目或论文复现任务，以及工作流上下文（由页面标题明确显示）。
- 工作流版本。
- 数据版本摘要。
- 状态。
- 运行时长。
- 开始时间。
- 操作。

如果空间不足，将数据版本、模板版本等次要信息作为主字段下方的辅助文本，而不是无限增加列宽。

行内展开只展示运行摘要、失败原因和关键产物；完整信息进入该工作流下的运行详情页。项目概览或工作台的汇总项仅用于定位，不另建跨项目运行列表页。

## UI-10.3 工作流运行详情页

建议采用顶部运行摘要 + 主内容分栏：

左侧或主区域：

- 工作流执行图。
- 节点状态。
- 当前执行进度。
- 失败节点和依赖影响。

右侧或辅助区域：

- 运行配置。
- 数据版本。
- 关键指标。
- 产物摘要。
- 运行日志入口。

对于宽屏，可采用左右分栏；较窄屏幕切换为 Tab，避免强制横向挤压。

## UI-10.4 节点运行详情抽屉

点击节点后展示：

- 输入数据引用。
- 参数快照。
- 开始 / 结束时间。
- 执行耗时。
- 输出产物。
- 错误代码与简明错误信息。
- 日志摘要。
- 重试或查看上游节点操作。

原始日志应可展开查看，但默认先展示人类可读的错误摘要和修复方向。

## UI-10.5 取消、重试与恢复

- 取消运行前说明会影响哪些节点。
- 重试应说明是重试失败节点还是重新运行整个工作流。
- 若使用缓存或复用已有产物，应在界面中明确标注。
- 不允许在前端显示“运行成功”而后端任务仍处于运行中。
- 运行失败后保留已经成功的分支产物，除非数据安全或任务语义要求清理。

# UI-11. 工作台论文复现模块与实验核验

## UI-11.1 模块定位与入口

论文复现模块位于工作台内部，与“项目”同级，用于回答“论文中的可核查主张能否在已知条件下复现”和“实验结果是否符合预先确定的核验规则”。用户可直接建立复现任务，无需先创建项目；任务可按需关联已有项目资源。入口包括工作台“论文复现”、工作流运行结果的“创建复现任务”，以及待复核事项。报告、图表、表格、模型权重、预测结果、日志和配置快照按任务或运行归档，供比较、复核和导出。

## UI-11.2 检验任务类型与输入

论文复现任务记录论文来源、待核查的具体主张、原文报告的指标或图表、方法与可用材料、许可或访问限制，以及预先设定的比较口径。将“文献报告值”“系统实际复算值”和“解释性推断”分别标注；缺少原始数据或关键方法时，标记为条件不足，不宣称完整复现。

实验核验任务记录实验目标、数据来源与版本、工作流及组件版本、参数与随机种子、预期指标或容差、实际运行 ID 和产物。支持同一条件下重跑、与基准运行对比，以及由授权人员复核偏差。指标、容差和判定方法应在运行前明确；未设定规则时，只展示比较结果，不自动给出“准确”结论。

## UI-11.3 检验任务列表与详情

工作台论文复现列表按任务类型、状态、关联项目（可选）、工作流、时间和复核人筛选。任务卡或表格展示核验对象、依据、最近运行、差异摘要与下一步操作。任务内可配置数据、选择模板、编辑工作流并查看运行；详情页至少包含：

- 核验主张或实验目标，以及可判定的范围。
- 论文依据或实验基准与数据版本。
- 关联工作流版本、运行记录、参数快照和环境说明。
- 原文或基准结果与实际结果的并排比较，包括指标单位、计算方法和容差。
- 偏差原因、缺失条件、限制与人工复核意见。
- 支撑结论的图表、表格、模型文件、日志与报告链接。

状态使用“待准备、条件不足、待运行、运行中、待复核、符合预设规则、存在差异、无法判定”等清晰措辞。运行成功仅说明执行完成，不自动表示论文复现成功或实验准确。任何结论都必须能回溯到输入、规则与实际运行。

## UI-11.4 检验报告与阅读页

检验报告列表优先使用紧凑表格或简洁卡片，并归属于工作台论文复现模块中的任务。报告阅读页采用文档阅读布局：

- 标题、生成时间和版本信息。
- 核验问题、范围和判定规则。
- 论文报告值或实验基准与实际结果。
- 方法、数据来源、参数和工作流版本。
- 图表、差异及可能原因。
- 限制、不确定性和人工复核记录。
- 运行与产物溯源。
- 导出操作。

报告页应优先保证文字和图表可读，不要放入复杂的节点编辑器侧栏。报告必须区分“尚待检验”“已完成运行”“符合预设规则”和“存在差异”。

## UI-11.5 证据卡

每条论文或实验依据至少展示：

- 标题或主张。
- 来源信息。
- 证据类型。
- 核查状态。
- 关联项目、工作流或报告。
- 证据强度或限制说明（只有有明确评估规则时才显示）。

必须区分文献中报告的结果、系统实际复算的结果、系统实际运行的代码结果，以及基于材料作出的解释。证据卡应链接到对应检验任务，不孤立陈列。

## UI-11.6 导出规范

- 报告支持 PDF / Markdown 等实际实现的格式。
- 表格支持 CSV / XLSX（按实现范围开放）。
- 图表支持 PNG / SVG（按图表引擎能力开放）。
- 导出时保留检验对象、判定规则、标题、方法说明、数据与工作流版本、运行 ID、差异、限制、复核记录和生成时间。
- 未实现的格式不要展示为可用按钮。

# UI-12. Agent 对话页面与提案

## UI-12.1 AI 助手的产品职责

Agent 对话具有独立一级导航和完整对话页面。进入时可开展研究讨论，也可引用项目、工作流或论文复现任务作为上下文；从具体对象打开对话时带入对象引用。用户应能清楚看到当前引用范围，并可切换或移除引用。

它可以协助：

- 理解研究目标。
- 推荐组件或模板。
- 生成工作流草稿。
- 解释工作流结构。
- 分析校验问题。
- 阅读真实运行结果。
- 提出下一步实验或分析建议。
- 生成报告草稿。

它不能伪造运行状态，也不能在没有权限和审批的情况下直接执行高风险操作。

## UI-12.2 页面布局

推荐采用“主对话区 + 上下文侧栏”的结构。

主对话区：

- 对话历史。
- 用户输入框。
- 附件和对象引用。
- 停止生成 / 重新生成等操作。

上下文侧栏：

- 当前项目。
- 当前工作流。
- 已引用数据集。
- 相关运行。
- 当前检验任务及其判定规则（如有）。
- 待审批提案。
- 工具调用记录。

如果空间有限，上下文侧栏可以折叠。不要将待审批提案永久堆在聊天记录顶部，导致对话空间被压缩。

## UI-12.3 提案卡

Agent 提出修改时，使用独立提案卡，而不是把重要操作藏在聊天气泡中。

提案卡包含：

- 提案目标。
- 影响对象。
- 变更摘要。
- 新增 / 删除 / 修改的节点与参数。
- 预计影响和资源需求（有依据时）。
- 校验状态。
- 批准、修改、拒绝操作。

批准前应能预览工作流差异。批准不代表跳过后端二次校验。

## UI-12.4 工具调用记录

工具调用结果采用可折叠记录，显示：

- 工具名称。
- 调用时间。
- 执行状态。
- 输入摘要。
- 输出摘要。
- 错误信息或产物引用。

默认不展示冗长的原始 JSON，但应允许授权用户查看完整技术详情。

## UI-12.5 Agent 状态与措辞

界面必须明确区分：

- 正在思考 / 规划。
- 正在调用工具。
- 已生成草稿。
- 等待用户批准。
- 任务已提交。
- 后端正在运行。
- 运行成功。
- 运行失败。
- 结果尚未验证。

避免使用“已完成科研”“已验证论文”等过度承诺的表述，除非系统确实完成了相应操作并保存了证据。

# UI-13. 个人信息与设置页面及辅助功能

## UI-13.1 个人信息与设置页面

本页具有独立一级导航，按常见软件的个人中心与设置方式组织；头像可作为快捷入口。建议分为：

- 个人资料。
- 界面偏好。
- 通知。
- 安全与会话。
- 工作空间与权限。
- 模型 / 服务连接（仅向有权限的用户开放）。

设置页面采用左侧设置目录 + 右侧表单内容，不需要把每一项设置都做成独立的大卡片。

## UI-13.2 通知

通知只用于真正需要用户处理的事件：

- 运行失败。
- 运行完成。
- 待审批提案。
- 数据质量阻断。
- 重要资源或权限变更。

提供已读状态和通知来源，避免无意义的提示轰炸。

## UI-13.3 可访问性与键盘操作

- 所有重要功能可通过键盘焦点访问。
- 焦点状态清晰可见。
- 状态不能只依赖颜色。
- 图表应提供标题、坐标轴和必要的文本摘要。
- 节点画布至少提供缩放、适配画布、删除、撤销和重做的快捷操作。
- 表单错误应与字段关联，并使用明确的文字说明。

# UI-14. 统一交互状态规范

每个页面和主要组件都必须覆盖以下状态，而不是只设计正常状态。

## UI-14.1 页面状态

- 初次加载、有数据、无数据、搜索无结果。
- 平台 API 断连、本机 runtime 不可用、外部网络/凭据不可用（分别呈现）。
- 本机数据待同步、同步冲突、权限不足、缓存过期或版本冲突。
- 运行中、等待外部、部分完成、失败和取消。

## UI-14.2 操作反馈

- 操作进行中：显示明确进度或加载状态。
- 操作成功：轻量反馈，并更新真实数据。
- 操作失败：说明原因、是否已产生部分结果和可采取的操作。
- 操作被阻断：定位阻断项，说明解决方法。
- 操作需要确认：展示影响范围，而非只有一个确认按钮。

## UI-14.3 空状态模板

空状态应包含：

1. 简洁图标或轻量插图。
2. 当前为什么为空。
3. 用户下一步可以做什么。
4. 一个主要引导动作（如适用）。

例如，工作流为空时显示“当前项目还没有工作流”，并提供“从模板创建”和“新建空白工作流”两个选择。不要只放一张大插画或一句“暂无数据”。

## UI-16.2 设计令牌集中管理

颜色、字号、间距、圆角、阴影和层级必须通过统一 token 或主题配置维护。禁止在各页面大量散落硬编码颜色和间距。

## UI-16.3 页面复用

- 列表页共用标题区、筛选栏、表格、分页和空状态。
- 详情页共用标题区、元数据区域、Tab 和操作区。

- 组件、模板和证据卡共用卡片结构，但允许字段不同。
- 工作流编辑器使用独立布局，避免强行复用常规后台页面的三栏结构。

## UI-16.4 技术选型原则

如果现有项目已经使用 React 与 Ant Design，可以优先统一设计 token、主题、布局和业务组件，而不是仅为换外观就整体重写。

节点画布可以使用 React Flow（`@xyflow/react`）或当前项目已有的成熟方案。具体选型应以现有代码、依赖和许可核查为依据。

技术栈应服务于体验和可维护性，不应因为追求“像某个产品”而无必要地更换框架。

# UI-17. 视觉与交互验收标准

每个页面完成后，至少通过以下检查。

## UI-17.1 视觉检查

- 页面标题、主要操作和内容区对齐。
- 全站字号、间距、圆角和边框规则一致。
- 每个主要区域有清晰的视觉层级。
- 不存在过量的卡片套卡片。
- 主色只突出关键操作。
- 图标风格统一。
- 表格密度适中，无不必要的横向滚动。
- 页面在 1280 × 720 和 1440 × 900 下均可用。
- 不依赖大面积渐变、强阴影或装饰性插画营造所谓高级感。

## UI-17.2 交互检查

- 所有看起来可点击的元素都有真实行为。
- 保存状态、运行状态和质量状态来自真实数据。
- 加载、空、失败、权限不足状态均有设计。
- 关键动作有明确反馈。
- 危险操作有影响说明和确认机制。
- 错误可以定位到相关对象。
- 用户可以从运行结果回溯数据、工作流和参数版本。
- 用户可以从工作台进入项目，再进入具体工作流并查看其运行；运行不占用独立导航入口。
- 顶部包含四个文字一级入口和两个图标入口；个人信息与设置可直接进入，仓库与科研支持图标具有名称提示与可访问标签。
- 工作台“项目”“论文复现”同级；新建复现任务无需先创建项目。
- 模板市场可直接进入，使用模板时明确目标项目或复现任务；Agent 对话可独立使用并引用对象上下文。
- 检验结论可回溯到预设规则、论文依据或实验基准、数据版本和实际运行；运行成功不会自动显示为检验通过。

## UI-17.3 工作流专项检查

- 节点可添加、配置、连接、删除和保存。
- 不兼容连接会被识别。
- 画布重载后工作流结构保持一致。
- 编辑与运行使用同一份工作流定义。
- 运行失败时可以定位失败节点。
- 节点详情可查看输入、参数、输出和日志。
- Agent 生成的草稿可以在画布中打开和编辑。
- 六段式只是模板，用户能够构建不同结构的工作流。

## UI-17.4 可用性检查

邀请未参与开发的成员执行任务：

1. 创建项目。
2. 选择一个模板。
3. 修改一个节点参数。
4. 增加一个分支或节点。
5. 运行并查看进度。
6. 定位一个预设错误。
7. 查看结果并追溯来源。

记录完成时间、误操作、求助次数和无法理解的文案，再根据问题迭代，而不是仅凭开发者主观判断界面是否美观。

# 第三篇 软件架构与实现方案

本篇据 V3.0 调整入口、独立复现任务、状态对象、模板优先级和开发阶段，其余科研组件、执行机制与场景要求保留。


# ENG-1 项目重新定位

## ENG-1.1 项目要解决的核心问题

当前科研软件虽然在文献检索、数据处理、模型训练、统计分析、实验管理和论文撰写等方面拥有大量工具，但科研人员往往需要自行组织研究过程，在多个软件之间切换，并手动传递数据、调整参数、保存结果和验证结论。

现有科研智能体也存在另一类问题：能够生成研究建议或调用少量工具，但难以把复杂研究任务转化为可编辑、可执行、可追踪和可复现的工作流。

本项目希望解决的不是简单的软件整合，而是：

1. 将科研能力封装成可以独立运行、自由组合和重复使用的标准化组件。
2. 将组件组合成能够适应不同科研任务的可视化工作流。
3. 让 Agent 能够理解研究目标，并根据实际情况生成、调整和执行工作流。
4. 将数据、文献、实验、模型、结果与研究结论组织成可追溯的科研项目。
5. 通过真实运行记录和证据核查，降低科研流程中的重复劳动、操作错误和结果不可复现问题。

## ENG-1.2 产品定位

平台定位为：

**以节点化工作流为执行基础、以 Agent 为智能规划与协作层、以标准化科研组件为能力单元的开放式科研工作平台。**

平台既不是固定步骤的科研向导，也不是单纯的 AI 聊天助手，更不是将多个独立软件简单放到同一个页面的工具集合。

它应当允许科研人员从一个简单操作开始，也允许专业用户构建复杂的科研场景。

## ENG-1.3 四项基本原则

### 原则一：工作流开放，不限制流程形态

六段式或其他线性流程仅作为入门模板。

复杂科研可以包含多路数据输入、多个研究分支、并行实验、不同模型比较、条件判断、循环优化、人工审批、外部实验等待、结果反馈以及多层级子工作流。

系统不应预设所有科研任务都必须经历相同的阶段。

### 原则二：组件统一，场景自由

同一个统计分析组件可以用于医学模型评价、生物实验数据分析和其他定量研究。

专业组件负责领域特定的操作，通用组件负责跨领域能力。工作流负责组织这些组件，而不是为每个场景重新编写一套固定流程。

### 原则三：Agent 驱动真实任务

Agent 需要实际调用组件和工具，创建工作流草稿，提交执行请求，读取运行结果，并根据结果决定后续行动。

只有发生了可检查的工具调用、状态变化和真实产物生成，才算完成相应科研操作。

### 原则四：复杂度开放，实施范围分阶段控制

平台的底层设计应支持未来扩展，但比赛版本不必一次性实现所有高级能力。

当前优先交付真正可用的节点编辑器、后端执行引擎、医学科研主场景和 Agent 工作流生成闭环。

# ENG-2 产品整体架构

## ENG-2.1 产品的五层结构

### 第一层：科研组件层

负责提供最小粒度的科研能力。

包括：

- 文献检索、论文解析和证据提取。
- 文件读取、数据导入和数据质量检查。
- 数据清洗、转换、统计分析与可视化。
- 实验设计、模型训练、模型推理和结果评价。
- 论文方法核查、代码运行、统计复算与结果比较。
- 报告生成、实验记录和科研结果导出。

每个组件都必须有明确的输入、输出、参数、执行方式和错误处理机制。

### 第二层：节点化工作流层

负责把组件连接为可以执行的研究任务。

用户能够在画布中自由增删节点、连接端口、配置参数、拆分研究分支、合并结果和保存工作流版本。前端保存声明式 JSON DAG；节点类型、输入输出和参数表单由注册表的契约生成。

系统根据节点之间的依赖关系建立 DAG 计划，而不是调用预先写死的固定流水线。用户请求一个或多个输出时，引擎只计划这些输出所依赖的祖先节点；未被请求的独立分支不执行。

### 第三层：Agent 智能协作层

负责将科研目标转化为工作流，并参与执行和迭代。

Agent 能够：

- 理解研究目标和约束。
- 查询可用节点、数据和研究资源。
- 规划工作流结构。
- 生成可编辑的工作流草稿。
- 检查参数、连接和数据依赖。
- 请求运行并跟踪状态。
- 解释结果、识别失败原因并提出修正方案。

### 第四层：项目、论文复现任务与证据层

负责管理项目与独立论文复现任务、数据集、文献、实验、模型、结果和报告之间的关系。论文复现任务可独立拥有工作流与资源，并可关联项目；关联不改变归属与访问权限。

每次重要运行都应关联对应的输入数据版本、工作流版本、节点参数、执行器版本和输出产物。

该层确保研究过程能够回溯，而不是运行结束后只留下几张图和一个结论。

### 第五层：科研应用层

将通用组件、专业组件和工作流封装成可直接使用的研究应用。

当前重点建设：

1. 医学 AI 科研应用。
2. 论文复现与审查应用。
3. 通用数据分析应用。
4. 少量生物科研扩展示范。

应用只是面向具体任务的产品入口，不应成为底层执行架构的限制。

---

节点化工作流在内部必须区分 `EditorDocument` 与 `ExecutionPlan`：前者包含布局、分组和交互状态；后者是由 compiler 生成的版本化执行 IR，只保存执行需要的节点、边、目标和资源约束。更换 React/画布不应改变执行语义。

## ENG-2.2 产品入口与技术分层的对应

顶部为工作台、模板市场、仓库图标、Agent 对话、科研支持图标、个人信息与设置。五层技术结构是内部职责分工，不对应五个导航页面。工作台内项目与论文复现并列；运行、版本、日志与产物从具体工作流进入。

仓库与科研支持本版只实现图标、名称提示和开放状态。云显卡与大模型算力供给属于后续服务接入，不作为当前图标入口的完成条件。

# ENG-3 节点化科研工作流系统

## ENG-3.1 工作流的定义

工作流是由科研组件实例、数据连接、执行依赖、控制规则和运行配置构成的可执行任务图。

工作流既可以简单，也可以复杂。

简单工作流可以只有两个或三个节点；复杂工作流可以包含多个并行分支、嵌套子工作流、循环迭代、人工决策和外部任务等待。

工作流不是一张静态流程图。它必须拥有能够被后端解释、校验和执行的结构化定义。

## ENG-3.2 工作流的基本构成

| 构成 | 职责 |
|---|---|
| 节点 | 代表一个科研操作、控制操作或外部任务 |
| 输入端口 | 接收数据、配置或上游结果 |
| 输出端口 | 提供数据、结果、状态或产物引用 |
| 数据连线 | 定义数据如何从一个节点传到另一个节点 |
| 控制依赖 | 定义节点何时能够执行 |
| 参数配置 | 指定节点的算法、阈值、资源和运行条件 |
| 控制结构 | 实现分支、汇合、循环、条件判断和等待 |
| 工作流版本 | 固定某一版节点、连接和参数定义 |
| 运行实例 | 记录一次具体执行及其状态、日志和结果 |
| 产物引用 | 指向数据集、模型、指标、图表、日志或报告 |

需要区分数据连接与控制依赖：两个节点可能需要先后执行，但不一定需要直接传递科研数据；反过来，数据连接也必须满足明确的数据类型要求。

P0 的执行图采用稳定节点 ID、组件 ID/版本、声明式参数和有向边表达；校验器拒绝未知节点、缺失必需端口、类型不兼容、重复/悬空引用和环路。运行从用户选定的输出节点反向收集依赖，再对其闭包拓扑排序；前端画布位置等纯展示数据不参与执行语义或缓存键。

数据边定义类型化数据依赖；控制边定义执行先后。运行从请求输出反向构建祖先闭包并消除无关分支。节点 `lazy` 输入的运行时需求解析是另一层机制：它允许节点按条件追加所需依赖，不等同于选择输出目标。

## ENG-3.3 节点分类

节点不应全部被当作普通的函数调用。建议分为以下类型。

### A. 数据节点

用于读取、引入、筛选和组织数据。

例如：

- 数据集选择。
- 文件导入。
- 数据库查询。
- 文献集合读取。
- 实验结果导入。
- 数据集拆分。
- 多数据源合并。

### B. 分析节点

用于完成具体科研操作。

例如：

- 数据质量检查。
- 数据清洗。
- 特征提取。
- 统计检验。
- 模型训练。
- 模型推理。
- 指标计算。
- 结果比较。
- 论文主张核查。

### C. 控制节点

用于管理复杂执行逻辑。

例如：

- 条件判断。
- 多分支路由。
- 并行分发。
- 结果汇合。
- 循环迭代。
- 子工作流调用。
- 人工审批。
- 外部任务等待。

### D. Agent 节点

用于在执行过程中引入受控的智能决策。

例如：

- 根据质量报告选择后续处理方案。
- 根据研究目标生成分析配置。
- 根据失败信息提出修复方案。
- 根据结果决定是否追加实验或继续优化。

Agent 节点应受到明确的输入、输出、工具权限、运行预算和停止条件约束。

### E. 产物节点

用于将研究结果组织为可使用的成果。

例如：

- 图表导出。
- 模型保存。
- 实验记录生成。
- 研究报告生成。
- 结果打包。
- 证据清单生成。

# ENG-4 复杂科研场景的表达能力

## ENG-4.1 设计目标

平台必须支持复杂科研任务的表达，但不要求所有复杂场景都在第一版完整实现。

底层数据模型需要能够描述复杂任务；执行引擎则按照开发阶段逐步开放对应能力。

## ENG-4.2 必须考虑的复杂控制结构

### 结构一：多分支并行

多个独立研究任务可以同时执行。

例如，将同一份经过质量检查的数据交给三个模型分别训练，再将三个模型的评价结果汇总比较。

### 结构二：条件分支

工作流根据真实运行结果选择不同路径。

例如：

- 质量检查通过：进入训练阶段。
- 质量检查失败：进入数据诊断和修复建议阶段。
- 结果达到预设标准：进入报告生成。
- 结果不达标：进入进一步分析。

条件必须由可检查的运行数据决定，不能只是画布上的装饰性分叉。

### 结构三：循环优化

某些科研任务需要多轮尝试。

例如，参数优化节点生成一组实验配置，训练节点运行，评价节点计算指标，判断节点决定是否继续搜索。

循环必须具有最大迭代次数、停止条件、资源预算和失败处理规则，避免无限执行。

### 结构四：结果汇合

不同分支产生的结果可以被统一比较、融合或汇总。

例如，将多个模型的预测、评价指标和运行配置汇入模型比较节点。

汇合节点必须检查输入是否具有可比性，不能简单地将不同任务的指标拼接在一起。

### 结构五：嵌套子工作流

用户可以把一个复杂的研究子任务封装成可复用的子工作流。

例如：

- 数据质量评估子工作流。
- 医学模型训练与评价子工作流。
- 论文结果核查子工作流。
- 统计分析与报告子工作流。

子工作流具有独立的输入输出接口、版本和运行记录，并能够被其他工作流调用。

### 结构六：人工审批与外部等待

部分科研任务不能完全自动完成。

例如，修改关键研究参数、启动高资源消耗的训练任务、提交外部数据、开展实际湿实验等操作，可以进入审批或等待状态。

当用户录入新的实验结果后，工作流可以从等待状态恢复执行。

## ENG-4.3 实施原则

P0 执行静态 DAG、输出目标裁剪、缓存感知依赖和资源受限调度。循环/动态条件和节点运行时新增依赖须由版本化 ExecutionPlan/扩展记录支持，分阶段开放；尚未支持的结构须在编译阶段阻断。

节点依赖就绪只代表图约束满足，不代表资源可用。调度必须分开处理 CPU、异步 I/O 和 GPU：I/O 可用有界 async 并发；CPU 使用有界 worker；GPU 按设备显存和模型驻留状态准入，容量未知或不足时排队/阻断，不能仅因 DAG 分支互不依赖就同时加载模型。

# ENG-5 节点协议与数据契约

## ENG-5.1 节点注册规范

每种节点类型必须由版本化声明契约定义；schema 是参数 UI、端口连线、服务端验证、执行器权限和文档的共同来源。契约至少包含：

- 唯一 component ID、schema/API 版本、实现摘要、名称与说明。
- 输入/输出端口 ID、强类型、必需/可选、多值、懒输入能力及领域元数据约束。
- 参数 schema（类型、默认值、范围、单位、UI widget 与跨字段校验）。
- 执行目标 `local` / `network` / `platform`、executor 绑定和版本。
- 依赖清单、环境和模型版本、安装/健康探测。
- 文件/网络/平台权限及 CPU、内存、GPU/显存、时长和并发需求。
- 幂等/确定性声明、缓存策略和失效条件。
- 异步完成方式、外部等待状态、错误分类、重试/取消策略。

工作流节点实例仅保存 component ID/版本、参数、端口绑定和布局；不携带代码、任意路径或凭据。P0 仅允许运行内置受控 registry 的执行器。

## ENG-5.2 端口类型

端口不仅要有名称，还必须声明数据类型和必要的约束。

第一阶段建议支持以下科研数据类型：

- `DatasetRef`：数据集引用。
- `ValidatedDatasetRef`：通过指定质量规则的数据集引用。
- `ImageBatchRef`：图像批次引用。
- `LabelSet`：标签集合。
- `PredictionSet`：预测结果集合。
- `MetricSet`：评价指标集合。
- `PaperClaimSet`：经过结构化整理的论文主张。
- `Comparison`：比较结果。
- `ExperimentRecord`：实验记录。
- `ReportRef`：报告引用。
- `ArtifactRef`：通用产物引用。

后续根据学科需求扩展结构化类型。

类型校验不能只检查名称。例如，两份预测结果即使都属于 `PredictionSet`，也必须核对任务类型、样本标识、类别顺序和数据拆分版本，才能确定是否可以比较。特殊泛型只可在注册组件契约明确声明时使用；不得用宽泛 `ANY` 绕过科研数据的必要约束。

类型可按领域分层并支持显式子类型兼容，例如 `media.image.rgb <: media.image`、`model.diffusion`、`data.number`。未知或宽泛 ANY 类型不得用来绕过端口校验；医学任务还要核对标签、样本 ID、拆分版本等元数据。

## ENG-5.3 参数配置

节点参数必须具有明确的校验规则。

例如，医学评价节点可以配置：

- 评价指标。
- Bootstrap 次数。
- 置信区间计算方式。
- 标签处理规则。

参数校验需要同时发生在前端和后端。前端用于及时提示，后端负责最终判定。

工作流 JSON 不允许直接包含任意 Python 或 Shell 命令、任意文件系统路径或密钥。本机文件先通过受控导入器进入资源库，以资源 ID、版本和内容哈希引用；节点仅获得注册时声明且用户已批准的文件能力。确需执行代码的科研节点必须通过受控执行环境调用，并具有单独的权限与资源限制。

# ENG-6 工作流编辑器与用户体验

## ENG-6.1 核心界面

工作流编辑器采用节点式画布，配合节点目录、参数配置面板和运行监控面板；编辑器从项目或论文复现任务进入。完整应用外壳、一级导航、布局与设计令牌遵循 UI 篇。

建议使用 React Flow（`@xyflow/react`）实现画布交互；具体版本和许可情况在开发时确认。

界面主要包括：

1. **节点目录：** 按通用科研、医学科研、论文审查和控制节点分类。
2. **工作流画布：** 增删节点、连线、断线、移动、缩放、分组和查看连接关系。
3. **参数面板：** 配置当前节点的输入、算法参数和运行条件。
4. **校验面板：** 展示缺失输入、类型冲突、权限问题和依赖错误。
5. **运行面板：** 显示执行状态、耗时、日志、失败原因和资源消耗。
6. **产物面板：** 查看每个节点生成的数据、指标、图表、模型或报告。
7. **版本面板：** 比较不同版本的节点、连线和参数变化。

## ENG-6.2 两种使用难度

### ENG-6.2 引导模式

普通科研人员从模板开始，系统只显示主要节点和必要参数。

用户可以直接修改模型、评价指标或数据源，不必理解整个底层架构。

### ENG-6.2 自由画布模式

用户可以打开完整画布，增加节点、调整连接、构建分支、修改高级参数和复用子工作流。

两种模式使用同一套节点定义、工作流版本和执行引擎，不能分别维护两套互不兼容的流程系统。

## ENG-6.3 必须避免的体验问题

- 画布可以连线，但无法保存。
- 保存后刷新，节点或连线丢失。
- 参数修改后没有影响真实执行。
- 节点失败只显示一个笼统的错误提示。
- 运行结束后无法查看各节点产物。
- Agent 生成的工作流无法在画布中打开。
- 复杂功能过多，导致新用户不知道从哪里开始。

核心体验应当是：用户可以从一个模板出发，理解每个节点的作用，修改工作流，运行并查看真实结果。

# ENG-7 工作流引擎与运行机制

## ENG-7.1 控制面、编译器与执行面

ICT 采用控制面与执行面分离的 typed workflow runtime：

1. **编辑器文档：** 桌面端画布保存可编辑 `EditorDocument`，含节点/边、布局、分组和 UI 状态。
2. **Workflow Compiler：** 规范化图、解析固定组件版本、检查 schema/类型/权限/依赖/资源，按目标输出做祖先闭包和无效节点裁剪，生成不可变 `ExecutionPlan` 与 `plan_hash`。执行 IR 不包含纯 UI 布局。
3. **控制面：** 管理对象归属、版本、审批、组件注册、计划提交、运行查询和同步策略；不直接执行科研代码。
4. **依赖引擎：** 使用 ready queue、阻塞计数和执行状态管理依赖；能表示运行时等待与受控依赖扩展。初版固定静态边，后续版本再启用节点 lazy input 和 ephemeral subgraph。
5. **执行面：** 本机 runtime 与平台 Worker 执行相同的 versioned component contract，但资源、权限和持久化独立。
6. **资源与产物服务：** 资源管理器决定 CPU/I/O/GPU 准入、模型驻留和执行并发；缓存保存签名到 Artifact handle 的映射，不把大张量长期塞进调度器内存。
7. **监督与观测：** 持久化 Run/NodeRun、计划哈希、事件、错误、缓存命中、资源用量和产物来源；worker 故障由监督层识别，不靠节点级 try/catch 假定隔离完成。

P0 不照搬 ComfyUI 的单队列和特定扩展代码；桌面 UI、平台服务和 CLI 将来均调用同一 ExecutionPlan 契约。

## ENG-7.2 编译与运行流程

1. 保存工作流编辑版本，并固定注册表版本、参数和资源输入快照。
2. 编译器检查节点/端口/类型/版本/权限/依赖和循环，生成不可变计划及哈希。
3. 用户选择目标输出；默认目标为组件契约显式标记的终端输出。计划只包含其上游依赖。
4. 运行前重新检查本机安装/缓存、外部网络/凭据、平台服务及设备资源。
5. 通过审批后创建 Run，绑定计划哈希、目标输出和输入快照。
6. ready queue 逐步放行可运行节点；检查签名缓存，再由资源管理器选择本机或平台 executor。
7. 异步节点进入 `WAITING_EXTERNAL`，等待 future/callback 后恢复；不把等待记成失败或闲置成功。
8. 受控节点可以请求尚未计算的 lazy input；下一阶段允许 compiler/runtime 记录其增量依赖或临时子图，不改写原始 EditorDocument。
9. 保存每次状态转移、输入输出、缓存来源、资源环境和日志；最后汇总 `succeeded` / `partially_succeeded` / `failed`。
10. 本地结果先持久保存在本机；用户显式同步后才上传并解决版本冲突。

审批必须绑定编辑版本/执行计划哈希、目标输出、输入、参数和外部副作用摘要。引擎处理步骤不映射成固定页面步骤。

## ENG-7.3 Ready queue、异步与故障边界

节点状态机：`WAITING` → `READY` → `RUNNING`；外部异步操作可进入 `WAITING_EXTERNAL` 后恢复；最终进入 `SUCCEEDED`、`CACHED`、`FAILED`、`BLOCKED`、`SKIPPED` 或 `CANCELLED`。工作流状态单独记录 `QUEUED`、`RUNNING`、`WAITING_EXTERNAL`、`SUCCEEDED`、`PARTIALLY_SUCCEEDED`、`FAILED`、`CANCELLED`。

调度按依赖和资源可行性共同决策：

- CPU 节点受 worker 数和内存配额限制。
- I/O 节点使用有界异步并发；网络节点记录 endpoint/授权并进入等待状态。
- GPU 节点按 device、显存预估、当前模型驻留和单设备并发上限准入；资源未知时串行或等待，不盲目并行。
- P0 不要求所有独立节点并行；保证有界运行和正确状态优先于并发吞吐。
- 节点异常只终止该节点和依赖它的下游；独立分支可按策略继续，整体标记部分完成。
- 故障隔离分为节点调用边界、独立 workflow context、worker 进程监督、插件进程隔离。节点异常捕获不替代 worker watchdog。

## ENG-7.4 签名缓存与产物

缓存 key 是确定性执行签名，不使用 workflow ID 或 node ID 作为唯一依据。推荐组成：

`hash(implementation_digest, schema_version, canonical_parameters, upstream_artifact_hashes, locked_dependencies, runtime_environment, model_revision, random_seed_or_nondeterminism_token)`。

组件必须声明 `cacheable`、有效期及副作用。非幂等节点、实时 HTTP/LLM 查询或时间敏感节点默认禁用缓存，或明确使用 TTL/nonce；随机训练只有种子、数据、模型和必要环境指纹满足策略时才缓存。缓存只有在产物存在、哈希完整、权限有效时命中；命中仍创建本次 NodeRun，并记录引用的原始 Artifact。

首版比赛闭环使用单一本机持久化签名缓存；缓存索引可存 SQLite，计算结果以内容寻址 ArtifactHandle 引用。命中仍创建本次 NodeRun，并记录复用产物的来源。多层 L1/L2 策略、跨进程共享缓存和平台 provider hook 列 P1；不得因清理缓存删除运行记录引用的产物。

## ENG-7.5 本地优先与混合执行

电脑端安装包应离线提供前端静态资源并启动独立本机 runtime；本机图、数据、模型依赖、ExecutionPlan、Run/NodeRun、事件、日志、cache index 和产物引用落本机事务存储。纯本地工作流无需平台 API、PostgreSQL、Celery 或互联网。

- `local`：调用已安装且依赖锁定的受控本机 executor；图、输入、模型和运行时全部在本机就绪时可离线运行。
- `network`：由本机 runtime 访问声明的端点；仅依赖网络、该端点和用户授权凭据。
- `platform`：依赖平台 API/Worker/GPU；平台断连时阻断该节点和依赖下游，不阻断独立本机分支。

比赛首批先交付静态 DAG 与 `local` 执行闭环，并为固定、受控网络端点接入 `network` adapter；本机已具备 Crossref 固定端点的首个网络组件。组件声明 `platform` 时必须依赖真实平台 Worker；注册表中没有匹配执行器时不得提交该节点，平台不可用时保留不依赖平台的本机分支。真实平台 Worker 属于 P0 后续切片，必须以真实服务/Worker 验收，不以合成 API 运行替代。

`WAITING_EXTERNAL` 描述节点执行协议（例如等待网络/API 回调），与平台断连状态区分。跨本机/平台传输必须明示来源、目标和数据授权，不自动上传敏感文件/凭据。同步使用 outbox；冲突、待同步结果可见，不静默覆盖。

离线创建的本机项目和工作流默认保持 `local_only`，联网、登录或恢复服务均不得触发自动同步。用户在本机项目页明确确认后，才创建或更新其平台副本；同步正文只包含项目元数据和工作流定义（名称、说明、画布结构及参数），本机文件、数据集内容、ArtifactHandle 实体、运行记录、报告和日志不随正文上传。平台 API 鉴权仍使用当前配置凭据；凭据不写入同步正文或本机 outbox。同步 outbox 在本机持久记录平台对象 ID、源修订、已同步平台修订及部分失败状态。后续同步先核对平台修订；发现平台版本已变化时保留双方内容并停止覆盖。创建请求结果不确定时，用户可填入已创建对象的 ID 继续关联；确认平台没有对应对象后才允许重试创建。工作流中的本机文件引用可以随定义保留为引用，但平台端不保证可访问，界面必须提示。

本机 loopback API 只接受有效的 HTTP `127.0.0.1`/`localhost` 来源（允许动态端口）并签发绑定来源的短期会话凭据；拒绝非 loopback 网页来源、任意代码、命令和绝对路径。依赖由安装包/审核组件包预置，不由节点自行联网安装。

## ENG-7.6 资源与模型运行时

P0 registry 声明 `ResourceRequest`；首版 runtime 对 CPU、内存、单次输入大小、时长和活动运行数执行保守的静态准入检查，超限时排队或阻断。该检查不构成 OS 级硬限额，也不代表已探测 GPU/显存。需要 GPU 的节点只有在匹配执行器和设备能力检查均可用时才允许运行；首版不实现动态显存调度、模型换入换出或自动安装依赖。资源管理与科研节点逻辑分离，持久输出以 ArtifactHandle 传递。

P1 将模型作为 `ModelHandle` 登记 revision、precision、RAM/VRAM 估算、placement、residency 和引用计数，由 model manager 统一复用/卸载；P2 再评估部分卸载/加载、异步权重 offload、多 GPU 放置和磁盘后备加载。ComfyUI 的 VRAM 专用机制不构成 ICT 对所有 GPU/框架均可用的保证。

## ENG-7.7 扩展 ABI 与安全

P0 定义带 API 版本的 component schema/lifecycle/health/permissions/dependencies/resource contract，且只启用经过审核的内置组件与受控 worker；第三方扩展默认关闭，不在 control-plane 进程动态 import 插件代码。

P1 完成签名包、依赖隔离、独立进程/容器沙箱 worker、健康检查与升级/回滚后，才允许启用第三方扩展，并通过 typed RPC/artifact handle 交换数据。公开插件市场和自动安装依赖列 P2。该边界与 ComfyUI 当前源码中兼容 V1 `NODE_CLASS_MAPPINGS`/V3 `comfy_entrypoint`、启动期 import 的实现不同，是 ICT 的安全选择。

# ENG-8 Agent 自动科研系统

## ENG-8.1 Agent 的角色

Agent 是科研工作流的智能规划、配置、调度与分析层，不应取代工作流引擎。

工作流引擎负责确定性执行、状态管理和安全校验；Agent 负责处理目标理解、任务规划、工具选择、异常分析和下一步决策。

这种分工既能实现智能化，也能保证研究过程可检查。

## ENG-8.2 Agent 的核心能力

### 能力一：理解研究目标

用户可以用自然语言描述研究任务。

例如：

“比较两个医学图像分类模型在同一验证集上的性能，检查数据泄漏风险，分析主要错误病例，并生成可追溯的评价报告。”

Agent 应将目标转化为明确的任务需求，包括输入数据、模型、评价指标、约束条件和最终产物。

### 能力二：检查资源和依赖

Agent 查询可用数据集、节点、模型和已有结果。

如果缺少必要数据、标签、模型权重或权限，应明确提出缺失项，而不是自行假设资源存在。

### 能力三：构建工作流

Agent 根据任务需求选择合适的节点，生成节点实例、参数和连接关系。

生成结果必须符合统一的工作流图结构，且可以被工作流服务校验。

### 能力四：执行和跟踪

在获得必要批准后，Agent 请求执行工作流，并持续读取真实运行状态。

它应能够区分排队、运行成功、运行失败和等待人工输入，不能将提交成功描述为科研任务已经完成。

### 能力五：结果解释与迭代

Agent 根据实际产物分析结果是否满足目标。

如果模型比较发现差异，Agent 可以进一步安排错误分析；如果质量检查失败，则可以提出数据修复方案；如果实验结果不足以支持研究主张，则应指出证据缺口。

后续任务必须建立在实际结果和可用资源之上。

## ENG-8.3 Agent 的任务循环

Agent 内部可以采用以下循环：

**理解目标 → 规划任务 → 检查资源 → 构建或调整工作流 → 校验 → 获批执行 → 读取结果 → 评价与反思 → 决定下一步 → 生成报告。**

这只是 Agent 的内部协作机制，并不是限制科研任务的固定流程。

如果任务简单，Agent 可以只调用一个组件。如果任务复杂，它可以生成包含多个分支和子工作流的执行图。

## ENG-8.4 工作流生成与审批

Agent 生成的图首先是草稿。

Agent 对话提案卡与所属项目或复现任务应清楚显示：

- 新增了哪些节点。
- 建立了哪些连接。
- 修改了哪些参数。
- 每个节点的作用是什么。
- 需要哪些数据和权限。
- 预计有哪些产物。
- 哪些操作需要审批。

用户可以修改草稿、重新校验，再根据操作风险决定是否批准执行。

高资源消耗、外部数据提交、关键研究参数变更及实际实验操作应具有明确的权限和审批机制。

## ENG-8.5 如何证明 Agent 真正实现了自动科研

不能仅以自然语言回答质量作为判断标准。

需要至少检查：

1. Agent 能否根据任务创建合法工作流。
2. 工作流能否在画布中打开和编辑。
3. 后端能否按图执行，而不是调用隐藏的固定流水线。
4. Agent 能否读取实际执行结果。
5. Agent 能否根据失败信息提出合理的修复方案。
6. Agent 能否根据真实结果创建下一轮任务。
7. 所有调用、审批、运行和产物是否可以追溯。

# ENG-9 AgentArts 与自研平台的协作

## ENG-9.1 职责划分

AgentArts 主要承担智能体的配置、推理、任务编排和工具调用。

自研科研平台负责：

- 工作流画布。
- 节点注册表。
- 工作流版本。
- 图结构校验。
- 运行调度。
- 科研数据和产物管理。
- 审批、权限和审计。
- 逐节点状态与报告。

AgentArts 不应成为科研数据、工作流版本和运行记录的唯一存储层。

## ENG-9.2 交互机制

通过 MCP 或受控 API，将 AgentArts 与科研平台连接。

AgentArts 负责生成符合协议的工作流草稿，并调用查询、校验、提案和状态查询工具。

科研平台负责验证图结构和权限，决定是否允许执行，并保存实际运行记录。

## ENG-9.3 建议的工具接口

| 工具 | 功能 |
|---|---|
| `get_project_overview` | 查询项目目标、数据和现有资源 |
| `get_reproduction_overview` | 查询独立复现任务的主张、判定规则、数据与工作流 |
| `list_node_types` | 查询可用节点及其输入输出 |
| `get_workflow_templates` | 查询可复用工作流模板 |
| `check_dataset_quality` | 运行或查询数据质量检查 |
| `validate_workflow` | 校验节点图、参数与依赖 |
| `create_workflow_draft` | 创建可编辑的工作流草稿 |
| `create_run_proposal` | 针对明确版本创建待审运行提案 |
| `get_workflow_run_status` | 查询运行状态及可用产物 |
| `get_artifact_metadata` | 查询产物类型、版本和来源 |

接口可以根据实际开发条件调整，但必须覆盖工作流生成、校验、执行提案和运行追踪。

## ENG-9.4 安全边界

- MCP 工具不能绕过后端权限校验。
- Agent 不得直接提交任意 Python 或 Shell 命令。
- 运行提案必须关联具体的工作流版本和内容哈希。
- 用户批准后，后端仍须重新检查图版本、数据版本和权限。
- 过期、被修改或不合法的提案不得启动任务。
- 工具调用失败时，Agent 必须报告失败，不得伪造运行结果。

# ENG-10 医学科研主场景

## ENG-10.1 场景定位

比赛阶段优先完成一个医学 AI 科研场景，以证明节点系统、科研组件和 Agent 能够协同工作。

可选任务包括胸部 X 光多标签分类或眼底图像青光眼筛查，最终以团队已有数据、算力和比赛要求为准。

医学场景是重点落地应用，不应反过来限制平台只能处理医学科研。

## ENG-10.2 基础节点包

建议先实现以下节点：

1. 数据集选择。
2. 标签读取。
3. 数据质量检查。
4. 患者级或样本级数据泄漏检查。
5. 图像预处理。
6. 模型加载或推理。
7. 模型训练。
8. 指标计算。
9. 模型比较。
10. 错误病例分析。
11. 可解释性结果展示。
12. 论文主张核查。
13. 结果报告生成。

每个节点都必须有明确的输入输出和真实执行结果。

## ENG-10.3 复杂医学科研示范

建议将双模型比较作为首个复杂工作流示范。

用户从同一份数据出发，先执行质量检查和数据划分，再将数据分叉给两个模型。两个模型分别产生预测结果，随后进入独立评价节点，最后汇总指标、比较差异并生成报告。

其中任一模型失败时，另一个独立分支的结果仍应保留；比较节点需要等待其必需输入，或者按照明确的缺失结果策略处理。

后续可以增加参数搜索、交叉验证、错误分析和多轮优化。

## ENG-10.4 医学场景的成果要求

最终产物应包括：

- 数据来源和质量报告。
- 实际运行的工作流版本。
- 模型配置和预测结果。
- 评价指标及必要的统计区间。
- 主要错误病例分析。
- 论文证据对比。
- 可追溯的研究报告。

所有结果都必须区分真实运行结果、预置演示结果和尚未完成的分析。

# ENG-11 论文复现与审查特色能力

## ENG-11.1 产品定位

论文复现是工作台内与项目并列的模块，可直接创建独立复现任务。任务包含论文依据、核验目标、预设规则、资源、工作流、运行、对比和报告；关联项目是可选操作。相关核验组件仍可嵌入医学模型比较、实验分析或其他研究工作流。

其目标不是简单地生成论文摘要，而是把论文中的方法、实验条件和结论转化为可以逐项核查的研究对象。

## ENG-11.2 组件能力

- 论文方法和研究主张提取。
- 数据、代码及补充材料登记。
- 实验条件整理。
- 指标口径核查。
- 统计结果复算。
- 可用代码的受控运行。
- 原论文与当前结果的差异分析。
- 证据充分性与限制说明。
- 复现或审查报告生成。

## ENG-11.3 工作流集成方式

论文审查节点可以位于研究开始阶段，帮助检查相关方法和主张；也可以位于研究结果阶段，将当前结果与论文报告结果进行比较。

它不需要固定处于某个阶段，具体位置由研究目标和数据依赖决定。

## ENG-11.4 独立任务与检验结论

任务需独立保存任务标识、所属工作空间、创建者、任务类型、论文来源、待核查主张、基准值、单位、容差、判定方法与规则版本；实验核验使用实验基准代替论文报告值。工作流与数据引用归属本任务，关联项目可以为空。

比较前固定基准和规则版本。若事后调整规则，生成新版本并重新核验，不覆盖旧结论。状态区分待准备、条件不足、待运行、运行中、待复核、符合预设规则、存在差异、无法判定；运行成功不会自动生成通过结论。复核记录包含复核人、时间、依据和意见。

## ENG-11.5 证据分级

系统必须明确区分：

- 已从原始材料中提取的信息。
- 已完成的统计复算。
- 已实际执行的代码复现。
- 仅根据现有材料作出的解释。
- 因缺少数据、代码或条件而无法核查的内容。

没有原始数据或代码时，不应声称完成了实证复现；没有真实湿实验记录时，不应声称完成了物理实验。

# ENG-13 项目、独立复现任务、版本和证据追溯

## ENG-13.1 项目数据模型

每个科研项目至少需要关联：

- 研究目标。
- 数据集与数据版本。
- 论文和证据。
- 工作流及其版本。
- 节点运行记录。
- 模型与实验配置。
- 运行产物。
- 研究结论和报告。

项目状态不是单纯的任务进度条，而是研究资源和研究结果之间的关系记录。

## ENG-13.2 独立复现任务与资源归属

项目和复现任务共用工作流服务、执行引擎及产物服务。每个工作流必须具有唯一归属：`owner_type=project|reproduction` 与 `owner_id`；复现任务另用可空的 `linked_project_id` 表达项目关联。所有对象保留 `workspace_id`，跨工作空间访问必须拒绝。

数据库需保证 owner 引用存在且类型匹配；可使用统一资源容器表加外键，或双外键加恰有一个非空的约束，不以裸 ID 和前端判断代替完整性校验。数据集与产物通过明确授权的资源引用参与工作流，关联项目不自动复制资源或授予权限。

模板实例化时创建目标容器内的工作流副本，并固定模板版本与来源；模板更新不改动已有实例。删除或归档项目时，独立复现任务的关联应解除或保留只读标记，不级联删除复现任务、历史运行及其证据。

## ENG-13.3 运行记录

每次工作流运行需要记录：

- EditorDocument 版本哈希、ExecutionPlan schema 版本/哈希和请求输出。
- 数据/模型版本、输入产物哈希、参数快照和随机种子。
- 节点 ID、component/schema/implementation 版本、执行目标、executor 和依赖环境指纹。
- 节点状态迁移、异步等待/恢复、动态扩展 subgraph 摘要、开始/结束时间和耗时。
- Cache signature、命中与原 Artifact 来源。
- CPU/RAM/GPU/显存预算和实际摘要、错误码、受控日志。
- 输入/输出 Artifact 及 checksum、操作者和审批。
- 本机同步批次、同步状态和冲突处理记录。

## ENG-13.4 可复现要求

用户应能够重新打开历史工作流，查看当时的配置和结果。

对于具备重跑条件的任务，应允许使用固定版本重新执行，并比较新旧结果。

如果依赖的数据、模型或外部服务已经变化，系统必须明确标记，不应将重新运行描述为与原运行完全相同。

---

缓存命中不是新的测量结果；报告中须显示实际执行、缓存复用和预运行结果的来源。对无法锁定的外部 API、模型或软件环境，说明不可复现范围。

# ENG-14 数据安全与执行安全

## ENG-14.1 数据访问

所有数据引用都必须由所属执行面的权限边界检查：平台 Worker 使用服务端授权，本机 runtime 使用本机账户、项目归属和已登记的文件/目录授权；不得只依赖编辑器 UI 校验。

工作流图中保存的是数据或产物引用，不应直接嵌入大型影像、模型文件或敏感数据内容。

## ENG-14.2 执行隔离

控制面只接收类型化输入和受控组件绑定，不执行工作流携带的代码。内置 executor 运行在可监督 worker；worker 具有文件白名单、网络策略、CPU/RAM/GPU/时长配额，工作流间运行上下文隔离。

第三方 extension 一旦启用，必须运行于独立进程或容器，使用版本化 typed RPC；不在 API/controller 进程 import 扩展。GPU tensor 或大文件通过受控 artifact handle/shared memory 等边界传递，日志/错误携带 run/node ID 且移除令牌和敏感原文。worker watchdog 负责检测卡死/崩溃；节点 try/catch 不能替代进程监督。

## ENG-14.3 运行审批

审批策略应根据操作风险确定。

低风险的只读分析可以采用较轻的审批方式；高资源消耗任务、关键研究参数修改和外部操作应使用更严格的确认机制。

## ENG-14.4 审计与恢复

系统应保留运行日志、审批记录和产物引用。

发生失败时，应能够定位失败节点，保留已完成分支的结果，并支持在符合条件时重试。

# ENG-15 开发范围与优先级

## ENG-15.1 P0：必须完成

P0 交付电脑端可运行的 typed workflow runtime 和真实离线纵向切片。比赛版按以下顺序推进；应用入口、项目/复现归属、模板和 Agent 功能边界仍按 UI 与 DEV 篇执行。

### P0-A：先完成表格前五项

1. Workflow Compiler：把 `EditorDocument` 编译成有 schema 版本和 `plan_hash` 的不可变 `ExecutionPlan`，解析组件版本并校验权限、类型、依赖和资源。
2. 类型化节点 Schema：沿用 `workflow_components.py` 的版本化契约，生成端口、参数表单和校验；声明节点版本、依赖、执行方式、权限及资源请求。
3. 按目标输出裁剪：用户选择报告/指标等输出后，只保留生成该输出所需的祖先依赖。
4. Ready Queue 与依赖阻塞：P0 只跑静态 DAG；失败阻断依赖它的下游，独立分支按策略继续。
5. 执行状态机与异步等待：至少支持 `READY / RUNNING / WAITING_EXTERNAL / SUCCEEDED / FAILED / BLOCKED / CANCELLED`；等待外部网络、AgentArts 工具或长任务时状态可恢复，不伪装为失败/成功。

### P0-B：接入离线 CSV 处理闭环

- 直接复用 ICT 旧桌面端 `desktop/ict_desktop/manifest_quality.py::inspect_manifest()`，通过本机 runtime 的受控 `local` executor 调用；不另写一套 CSV 结构检查逻辑。
- 提供 `ict.data.csv_select_columns` 本机节点，按精确字段名逐行筛选/重排并生成派生 ArtifactHandle；原始文件只读保留，产物记录来源节点、Run、输入产物和哈希。
- runtime 负责本机文件授权、输入版本快照、SHA-256、Run/NodeRun、ArtifactHandle 和报告持久化；选择器不装载整份 CSV 到内存，结构检查器只返回结构统计与问题明细，不保存记录原文。
- 平台 API 与互联网关闭时，用户仍可执行“选取 CSV → 可选字段筛选 → 结构预检 → 查看报告”；报告始终标注“结构预检，不是科研结果”，不等同于数据科学质量或论文复现。

### P0-C：补基础缓存、资源准入、执行路由与故障监督

- 缓存先做单一本机持久化 Input Signature 缓存（SQLite 索引到本机 ArtifactHandle 输出引用）；签名覆盖实现摘要、组件/Schema 版本、规范化参数、上游产物哈希及所需运行环境，随机种子/模型版本在对应组件需要时纳入。非幂等、时间敏感或外部查询默认不缓存；命中仍写本次 NodeRun。进程 L1、多层共享和跨 Worker 缓存后置。
- ArtifactHandle 传递类型化产物引用、内容哈希、授权状态和生成 Run/NodeRun，不把大文件或张量放进调度器长期内存。
- 先做声明值资源准入：限制 CPU/内存、时长、输入大小和活动运行数；只有存在对应 executor 与设备能力声明时才允许 GPU 节点。首版不自动探测显存、做模型迁移或 offload；无法确认的资源请求明确阻断或排队。
- 分别记录节点业务错误、workflow 部分失败和本机 runtime Worker 异常；监督后台任务并在 runtime 重启后标记未完成运行。`local / network / platform` 根据各自依赖逐节点判断，恢复联网后通过显式 outbox 同步；真实平台 Worker 以真实服务验收，进程池隔离和插件沙箱后置。

# ENG-16 技术架构与实现建议

## ENG-16.1 前端

采用 React 与 React Flow 构建节点画布。

前端按“全局应用外壳 → 模块页面 → 对象详情 → 工作流编辑器”组织。应用外壳负责六个一级入口；模块页面包含工作台、模板市场、Agent 对话、个人信息与设置；工作台提供项目和论文复现两个分支；编辑器复用画布、属性、运行和产物面板。

前端重点实现：

- 节点和端口渲染。
- 拖拽和连线。
- 参数编辑。
- 图结构校验提示。
- 版本保存。
- 运行状态展示。
- 产物预览。

前端只负责编辑和展示，不负责决定最终的执行权限或执行顺序。

## ENG-16.2 后端与执行面

控制面沿用 Python/FastAPI 管理工作空间、对象归属、节点 registry、compiler/validation、计划哈希、审批、平台运行和结果查询。本机 runtime 作为独立桌面进程，提供本机 API、compiler/execution adapter、本机 SQLite/事务存储、artifact/cache、资源探测和同步 outbox。

本机 runtime 与平台 Worker 共享 component manifest、ExecutionPlan 和 Run/NodeRun 语义，但独立部署、状态和权限检查。CPU worker、async IO、GPU scheduler 和 plugin sandbox 通过 execution adapter 分流；控制面不 import 或执行插件代码。

## ENG-16.3 存储

结构化数据保存对象归属、组件/schema 版本、EditorDocument、不可变 ExecutionPlan、运行/节点状态、签名、错误和同步记录。大型文件、模型权重和输出存受控 Artifact store；cache 仅存 artifact handle 和 producer/signature 元数据。

本机使用事务数据库和内容寻址文件目录，保存必要离线资源和 outbox；平台使用受控数据库/对象存储。L1 process cache、L2 local disk 和后续共享 L3 分开管理；缓存淘汰不得删除仍被运行记录引用的 Artifact。

## ENG-16.4 AgentArts 接入

通过 MCP 或 API 调用受控的科研工具。

AgentArts 内部的智能体工作流与用户可编辑的科研工作流需要明确区分：

- 前者负责智能体内部推理与工具调用。
- 后者负责用户科研任务的节点编排与实际执行。

两者通过受控工具交换符合科研工作流协议的草稿与结果引用；AgentArts 内部编排定义无需与科研图相同。工具必须携带工作空间和目标对象归属，目标可以是项目或独立复现任务。

# ENG-17 团队分工与协作

## R1：科研任务与数据负责人

主要职责：

- 确定医学科研主任务和可用数据。
- 定义数据质量规则与评价指标。
- 整理医学科研节点的输入输出。

# ENG-18 开发阶段与里程碑

原计划中的 W0–W3 已经过期，因此后续按工程里程碑推进，不再沿用已经失效的日历安排。具体日期由团队根据比赛截止时间和当前代码状态确定。

## 阶段 0：统一入口与资源归属

先盘点已有代码，按已实现、部分实现、未实现、无法确认列出差距。建立顶部四个文字入口与两个图标、工作台项目/论文复现同级分支、项目与复现任务数据归属。接入可用的个人信息与设置，建立基础内置模板目录；Agent 对话先提供页面和明确连接状态。

验收：可从工作台独立创建项目和复现任务；两种容器可分别持久化工作流；模板实例化不会串入其他容器；入口与状态真实，图标有标签且不会跳到伪造页面。

## 阶段 A：工作流协议与最小画布

目标：固定编辑格式与执行 IR 的边界。

1. 定义版本化组件 manifest、强类型端口和参数 schema。
2. 定义 EditorDocument 与规范化 ExecutionPlan 两种图表示。
3. 定义编译校验、组件版本解析、目标输出和 plan hash。
4. 实现画布保存、加载、版本恢复以及 schema 一致性校验。
5. 定义本机 runtime API、桌面资源包和本机数据路径安全边界。

验收：图刷新和恢复一致；UI 布局变化不改变 ExecutionPlan 哈希；未知组件、缺端口、不兼容类型和环路在执行前被拒绝。

## 阶段 B：比赛版工作流执行纵向切片

按 B1 → B2 → B3 交付；每一段都可单独演示和验收。

### B1：先打通前五项执行骨架

实现 Workflow Compiler、类型化 Schema、目标输出依赖闭包、静态 ready queue/依赖阻塞，以及含 `WAITING_EXTERNAL` 的状态机。先使用可确定的小型内置节点完成编辑、编译、执行与节点记录。

验收：编辑图编译成不可变 `ExecutionPlan`；端口/参数/组件版本错误在运行前报告，执行前核对权限、已安装依赖和资源准入；选择一个输出时无关分支不运行；依赖失败只阻断下游；异步等待可恢复并能取消/超时。

### B2：复用 ICT CSV 检查器形成离线演示闭环

先落本机 runtime、最小 Run/NodeRun 和 ArtifactHandle，再把 `inspect_manifest()` 注册为受控 `local` executor。记录文件来源、授权选择和 SHA-256，只持久化结构报告，不留原始行内容。

验收：平台 API、数据库和互联网关闭后，用户仍可选择本机 CSV、运行预检并读取报告；报告明确“结构预检，不是科研结果”；输入哈希和运行/产物关系可追溯。

### B3：基础缓存、资源保护和故障监督

增加单一本机签名缓存、基于组件声明的 CPU/RAM/输入大小/时长/并发准入，以及后台任务异常记录和 runtime 重启恢复；同时按节点执行目标接入最小 `local / network / platform` 路由。`local` 节点只依赖本机 runtime 与已安装依赖，`network` 节点检查互联网及目标服务，`platform` 节点检查平台 API。平台不可用时，不影响依赖齐全的本机分支；只阻断依赖不可用执行目标的节点及其下游。恢复连接后通过显式同步和 revision 冲突保护合并，不静默覆盖本机草稿。

验收：同一有效签名显示缓存来源且保留本次 NodeRun；外部调用按策略禁用缓存；声明资源超过静态预算时排队/阻断；节点错误、workflow 部分失败和后台任务/重启故障可区分；平台 API 不可用时纯本地预检仍可执行，网络节点和平台节点分别按其依赖状态阻断；平台恢复后本机草稿与较新平台 revision 冲突时保留两侧内容并要求核对，用户确认覆盖平台可变草稿前先将其固化为不可变版本；核对或保存期间 revision 再次变化时刷新平台内容并停止覆盖。首版只做保守准入与同进程任务监督，不做 OS 级资源硬限额、多层共享缓存、动态显存调度或独立 Worker 进程池。

## 阶段 C：医学科研主闭环

目标：形成完整且可追溯的医学科研演示。

任务：

1. 实现数据集选择和质量检查。
2. 实现医学图像预处理或模型输入准备。
3. 接入至少两个可比较的模型实例或模型配置。
4. 实现模型评价。
5. 实现结果比较。
6. 实现报告生成。
7. 在工作台独立复现任务中固定一项论文主张或实验基准与判定规则，引用实际运行进行比较并保存复核记录。

验收：一份固定的演示数据能够通过实际运行得到质量报告、评价结果和最终报告；独立复现任务可基于真实产物完成一次基本对比。

## 阶段 D：AgentArts 工作流生成

目标：让 Agent 根据科研目标创建真正可执行的工作流草稿。

任务：

1. 暴露节点目录查询工具。
2. 暴露工作流模板查询工具。
3. 暴露工作流校验工具。
4. 暴露工作流草稿创建工具。
5. 暴露运行状态查询工具。
6. 实现草稿编辑、审批和后端复核。

验收：Agent 生成的工作流能够打开、修改、校验和运行；无效草稿无法启动执行。

## 阶段 E：特色能力与稳定性

目标：深化独立论文复现模块的证据核查、异常恢复和答辩准备。P0 的任务与基本对比在阶段 B/C 随最小真实运行闭环建立，本阶段扩展核查深度。

任务：

1. 完善工作台论文复现任务的论文主张、预设规则、证据核查与人工复核。
2. 实现结果比较与报告追溯。
3. 测试非法参数、错误连接和运行失败。
4. 测试版本变更与审批失效。
5. 完成部署、操作说明和演示录制。
6. 有余量时增加生物扩展示范。

验收：整个演示从项目启动到结果报告可重复运行，并且所有关键结果都有对应的运行记录。

# ENG-19 项目验收标准

## ENG-19.1 节点编辑验收

- 可以添加、删除和移动节点。
- 可以连接和断开端口。
- 可以配置参数。
- 可以保存并恢复工作流。
- 可以创建不同版本。
- 可以识别缺失输入和不兼容类型。

## ENG-19.2 执行引擎验收

- 编辑器文档编译为版本化 ExecutionPlan；plan hash 不含布局状态。
- 目标输出仅执行所需依赖；节点 lazy input 若启用则将增量依赖记入运行 lineage。
- 首个 CSV 节点可在本机离线运行；仅保存授权来源、输入 SHA-256 和结构报告 Artifact，不留原始行内容，且明确不是科研结论。
- 类型、权限、依赖、循环和资源在启动前校验。
- Ready queue 状态可观测；异步节点正确等待和恢复；CPU/IO/GPU 并发受各自配额约束。
- 签名缓存包含实现、schema、参数、上游产物和运行环境；命中有来源且随机/非幂等节点不会错误复用。
- 失败隔离到节点、workflow context 和 worker 边界；独立分支结果保留，整体状态准确表示部分完成。
- 断开平台服务与网络后，本机缓存的纯 `local` 工作流可执行；`network` 和 `platform` 分别按依赖阻断。
- 本机和平台运行共享组件契约并分别持久化；恢复连接后显式同步，不静默覆盖。

## ENG-19.3 Agent 验收

- Agent 能够查询节点能力。
- Agent 能够生成结构化工作流草稿。
- 工作流草稿能够在画布中打开。
- Agent 能够读取真实运行状态。
- Agent 能够基于实际失败信息提出修正方案。
- Agent 不得伪造未执行的科研结果。

## ENG-19.4 科研结果验收

- 数据质量报告来自真实运行。
- 模型指标由实际预测结果计算。
- 论文比较具有明确的证据来源。
- 报告可以追溯到数据、模型和运行版本。
- 结果不足时能够明确标记不确定性与限制。

## ENG-19.5 信息架构与任务归属验收

- 六个一级入口与 UI 篇一致，个人信息与设置有独立一级入口。
- 仓库和科研支持只需图标、名称、开放状态；科研支持说明云显卡与大模型算力用途。
- 工作台项目与论文复现并列，复现任务不依赖先创建项目。
- 模板市场可独立进入，并将指定版本实例化到选择的目标。
- Agent 对话独立可用，并可显式引用项目或复现任务。
- 运行只从具体工作流进入；独立任务与项目资源不会因关联关系越权访问。
- 个人资料及偏好修改持久化并可重载；不提供无效保存按钮。

## ENG-19.6 用户体验验收

邀请一名未参与核心开发的队员完成以下操作：

1. 从模板市场打开医学科研模板，选择项目后实例化。
2. 增加一个模型分支。
3. 配置并保存工作流。
4. 运行工作流。
5. 查看评价结果。
6. 定位并处理一个预设错误。
7. 打开最终报告并追溯结果。

如果用户只能在开发人员指导下完成这些操作，说明界面和交互仍需要优化。

# ENG-20 风险与应对

## 风险一：画布完成，但后端仍然是固定流水线

**应对：** 在开发最早期就实现最小图执行器，以实际修改连线改变执行路径作为阶段验收条件。

## 风险二：Agent 只能输出文字，不能创建工作流

**应对：** 统一 Agent 与画布使用的工作流数据协议，先实现结构化草稿创建，再逐步增加智能规划能力。

## 风险三：功能太多，导致比赛版本无法完成

**应对：** 以 P0 为硬性范围，优先完成节点图、执行器、医学闭环和 AgentArts 接入；复杂控制结构按阶段增加。

## 风险四：论文审查被误认为真正的论文复现

**应对：** 分开记录文献提取、统计复算、代码复现和实际实验状态，明确每项证据的可核查范围。

## 风险五：复杂工作流导致执行不可控

**应对：** 设置循环上限、超时、资源预算、权限检查和失败恢复机制。所有执行都必须由本机 runtime 或平台服务在所属执行面校验，不得只依赖客户端 UI。

## 风险六：演示依赖预置结果，无法证明真实能力

**应对：** 固定演示数据与预期结果，现场执行至少一个真实节点；同时保留完整运行记录，并准确区分预运行结果和现场执行结果。

---

## 风险七：把节点异常捕获误当作故障隔离

**应对：** 分离节点调用、workflow context、worker 进程和插件进程故障域；使用 watchdog、持久状态与重启后可判定的运行记录。

## 风险八：复制 ComfyUI 运行机制但忽略 ICT 运行边界

**应对：** 每项借鉴都注明采用层级和范围；保持本机/平台双执行面、资源授权和敏感数据同步策略，不把 ComfyUI 源码行为描述成 ICT 现成功能。

# ENG-21 最终产品形态

最终产品应提供三种相互衔接的使用方式。

**直接使用组件：** 用户选择一个科研功能，提供输入并获得结果。

**可视化工作流：** 用户自由编排节点，搭建适合当前研究任务的执行图。

**Agent 驱动科研：** 用户描述研究目标，由 Agent 生成、校验和调整工作流，并在获得必要授权后执行，随后根据结果推进后续研究。

三种方式使用同一套科研组件、工作流协议、执行引擎和产物管理机制。直接使用组件时，也应在所属项目或复现任务中创建单节点工作流并记录运行，不另设全局运行入口。三种方式是使用方式，不替代 UI 篇规定的六个一级入口。

工作流模板负责降低使用门槛，专业组件负责扩展学科能力，Agent 负责提高规划和执行效率。

它们都不应限制用户构建复杂科研场景的能力。

## 项目最终目标

建设一个真正能够将科研目标转化为可执行任务、将科研工具组合成复杂工作流、将执行结果转化为可追溯证据的智能科研平台。

比赛阶段以医学科研闭环证明系统有效，以论文复现与审查展示科研可靠性，以生物组件展示跨学科扩展能力。

更长期的目标是让科研人员能够从一个简单任务开始，逐步构建更复杂的研究场景，并让 Agent 在明确的权限、数据和证据约束下，持续协助推进科研工作。
