# 模块化智能科研软件项目方案 V3.0

# 第一章 项目重新定位

## 1.1 项目要解决的核心问题

当前科研软件虽然在文献检索、数据处理、模型训练、统计分析、实验管理和论文撰写等方面拥有大量工具，但科研人员往往需要自行组织研究过程，在多个软件之间切换，并手动传递数据、调整参数、保存结果和验证结论。

现有科研智能体也存在另一类问题：能够生成研究建议或调用少量工具，但难以把复杂研究任务转化为可编辑、可执行、可追踪和可复现的工作流。

本项目希望解决的不是简单的软件整合，而是：

1. 将科研能力封装成可以独立运行、自由组合和重复使用的标准化组件。
2. 将组件组合成能够适应不同科研任务的可视化工作流。
3. 让 Agent 能够理解研究目标，并根据实际情况生成、调整和执行工作流。
4. 将数据、文献、实验、模型、结果与研究结论组织成可追溯的科研项目。
5. 通过真实运行记录和证据核查，降低科研流程中的重复劳动、操作错误和结果不可复现问题。

## 1.2 产品定位

平台定位为：

**以节点化工作流为执行基础、以 Agent 为智能规划与协作层、以标准化科研组件为能力单元的开放式科研工作平台。**

平台既不是固定步骤的科研向导，也不是单纯的 AI 聊天助手，更不是将多个独立软件简单放到同一个页面的工具集合。

它应当允许科研人员从一个简单操作开始，也允许专业用户构建复杂的科研场景。

## 1.3 四项基本原则

### 原则一：工作流开放，不限制流程形态

六段式或其他线性流程仅作为入门模板。

复杂科研可以包含多路数据输入、多个研究分支、并行实验、不同模型比较、条件判断、循环优化、人工审批、外部实验等待、结果反馈以及多层级子工作流。

系统不应预设所有科研任务都必须经历相同的阶段。

### 原则二：组件统一，场景自由

同一个统计分析组件可以用于医学模型评价、生物实验数据分析和其他定量研究。

专业组件负责领域特定的操作，通用组件负责跨领域能力。工作流负责组织这些组件，而不是为每个场景重新编写一套固定流程。

### 原则三：Agent 驱动真实任务

Agent 需要实际调用组件和工具，创建工作流草稿，提交执行请求，读取运行结果，并根据结果决定后续行动。

只有发生了可检查的工具调用、状态变化和真实产物生成，才算完成相应科研操作。

### 原则四：复杂度开放，实施范围分阶段控制

平台的底层设计应支持未来扩展，但比赛版本不必一次性实现所有高级能力。

当前优先交付真正可用的节点编辑器、后端执行引擎、医学科研主场景和 Agent 工作流生成闭环。

# 第二章 产品整体架构

## 2.1 产品的五层结构

### 第一层：科研组件层

负责提供最小粒度的科研能力。

包括：

- 文献检索、论文解析和证据提取。
- 文件读取、数据导入和数据质量检查。
- 数据清洗、转换、统计分析与可视化。
- 实验设计、模型训练、模型推理和结果评价。
- 论文方法核查、代码运行、统计复算与结果比较。
- 报告生成、实验记录和科研结果导出。

每个组件都必须有明确的输入、输出、参数、执行方式和错误处理机制。

### 第二层：节点化工作流层

负责把组件连接为可以执行的研究任务。

用户能够在画布中自由增删节点、连接端口、配置参数、拆分研究分支、合并结果和保存工作流版本。

系统根据节点之间的依赖关系确定执行顺序，而不是调用预先写死的固定流水线。

### 第三层：Agent 智能协作层

负责将科研目标转化为工作流，并参与执行和迭代。

Agent 能够：

- 理解研究目标和约束。
- 查询可用节点、数据和研究资源。
- 规划工作流结构。
- 生成可编辑的工作流草稿。
- 检查参数、连接和数据依赖。
- 请求运行并跟踪状态。
- 解释结果、识别失败原因并提出修正方案。

### 第四层：科研项目与证据层

负责管理研究任务、数据集、文献、实验、模型、结果和报告之间的关系。

每次重要运行都应关联对应的输入数据版本、工作流版本、节点参数、执行器版本和输出产物。

该层确保研究过程能够回溯，而不是运行结束后只留下几张图和一个结论。

### 第五层：科研应用层

将通用组件、专业组件和工作流封装成可直接使用的研究应用。

当前重点建设：

1. 医学 AI 科研应用。
2. 论文复现与审查应用。
3. 通用数据分析应用。
4. 少量生物科研扩展示范。

应用只是面向具体任务的产品入口，不应成为底层执行架构的限制。

# 第三章 节点化科研工作流系统

## 3.1 工作流的定义

工作流是由科研组件实例、数据连接、执行依赖、控制规则和运行配置构成的可执行任务图。

工作流既可以简单，也可以复杂。

简单工作流可以只有两个或三个节点；复杂工作流可以包含多个并行分支、嵌套子工作流、循环迭代、人工决策和外部任务等待。

工作流不是一张静态流程图。它必须拥有能够被后端解释、校验和执行的结构化定义。

## 3.2 工作流的基本构成

| 构成 | 职责 |
|---|---|
| 节点 | 代表一个科研操作、控制操作或外部任务 |
| 输入端口 | 接收数据、配置或上游结果 |
| 输出端口 | 提供数据、结果、状态或产物引用 |
| 数据连线 | 定义数据如何从一个节点传到另一个节点 |
| 控制依赖 | 定义节点何时能够执行 |
| 参数配置 | 指定节点的算法、阈值、资源和运行条件 |
| 控制结构 | 实现分支、汇合、循环、条件判断和等待 |
| 工作流版本 | 固定某一版节点、连接和参数定义 |
| 运行实例 | 记录一次具体执行及其状态、日志和结果 |
| 产物引用 | 指向数据集、模型、指标、图表、日志或报告 |

需要区分数据连接与控制依赖：两个节点可能需要先后执行，但不一定需要直接传递科研数据；反过来，数据连接也必须满足明确的数据类型要求。

## 3.3 节点分类

节点不应全部被当作普通的函数调用。建议分为以下类型。

### A. 数据节点

用于读取、引入、筛选和组织数据。

例如：

- 数据集选择。
- 文件导入。
- 数据库查询。
- 文献集合读取。
- 实验结果导入。
- 数据集拆分。
- 多数据源合并。

### B. 分析节点

用于完成具体科研操作。

例如：

- 数据质量检查。
- 数据清洗。
- 特征提取。
- 统计检验。
- 模型训练。
- 模型推理。
- 指标计算。
- 结果比较。
- 论文主张核查。

### C. 控制节点

用于管理复杂执行逻辑。

例如：

- 条件判断。
- 多分支路由。
- 并行分发。
- 结果汇合。
- 循环迭代。
- 子工作流调用。
- 人工审批。
- 外部任务等待。

### D. Agent 节点

用于在执行过程中引入受控的智能决策。

例如：

- 根据质量报告选择后续处理方案。
- 根据研究目标生成分析配置。
- 根据失败信息提出修复方案。
- 根据结果决定是否追加实验或继续优化。

Agent 节点应受到明确的输入、输出、工具权限、运行预算和停止条件约束。

### E. 产物节点

用于将研究结果组织为可使用的成果。

例如：

- 图表导出。
- 模型保存。
- 实验记录生成。
- 研究报告生成。
- 结果打包。
- 证据清单生成。

# 第四章 复杂科研场景的表达能力

## 4.1 设计目标

平台必须支持复杂科研任务的表达，但不要求所有复杂场景都在第一版完整实现。

底层数据模型需要能够描述复杂任务；执行引擎则按照开发阶段逐步开放对应能力。

## 4.2 必须考虑的复杂控制结构

### 结构一：多分支并行

多个独立研究任务可以同时执行。

例如，将同一份经过质量检查的数据交给三个模型分别训练，再将三个模型的评价结果汇总比较。

### 结构二：条件分支

工作流根据真实运行结果选择不同路径。

例如：

- 质量检查通过：进入训练阶段。
- 质量检查失败：进入数据诊断和修复建议阶段。
- 结果达到预设标准：进入报告生成。
- 结果不达标：进入进一步分析。

条件必须由可检查的运行数据决定，不能只是画布上的装饰性分叉。

### 结构三：循环优化

某些科研任务需要多轮尝试。

例如，参数优化节点生成一组实验配置，训练节点运行，评价节点计算指标，判断节点决定是否继续搜索。

循环必须具有最大迭代次数、停止条件、资源预算和失败处理规则，避免无限执行。

### 结构四：结果汇合

不同分支产生的结果可以被统一比较、融合或汇总。

例如，将多个模型的预测、评价指标和运行配置汇入模型比较节点。

汇合节点必须检查输入是否具有可比性，不能简单地将不同任务的指标拼接在一起。

### 结构五：嵌套子工作流

用户可以把一个复杂的研究子任务封装成可复用的子工作流。

例如：

- 数据质量评估子工作流。
- 医学模型训练与评价子工作流。
- 论文结果核查子工作流。
- 统计分析与报告子工作流。

子工作流具有独立的输入输出接口、版本和运行记录，并能够被其他工作流调用。

### 结构六：人工审批与外部等待

部分科研任务不能完全自动完成。

例如，修改关键研究参数、启动高资源消耗的训练任务、提交外部数据、开展实际湿实验等操作，可以进入审批或等待状态。

当用户录入新的实验结果后，工作流可以从等待状态恢复执行。

## 4.3 实施原则

第一阶段优先支持有向无环图、并行节点、基础条件分支和结果汇合。

循环、子工作流和持久等待可以根据实际工期逐步实施。

即使第一版尚未支持所有高级控制结构，也必须保证节点、边、数据类型和执行器架构不会阻碍未来增加这些能力。

# 第五章 节点协议与数据契约

## 5.1 节点注册规范

每种节点类型必须在节点注册表中定义其能力，而不是通过前端名称判断如何执行。

每个节点类型至少包含：

- 唯一类型标识。
- 节点版本。
- 显示名称和说明。
- 输入端口定义。
- 输出端口定义。
- 参数配置规则。
- 执行器绑定。
- 权限要求。
- 超时和资源限制。
- 缓存策略。
- 错误类型与处理规则。

节点实例只保存具体配置和连接，不直接携带任意可执行代码。

## 5.2 端口类型

端口不仅要有名称，还必须声明数据类型和必要的约束。

第一阶段建议支持以下科研数据类型：

- `DatasetRef`：数据集引用。
- `ValidatedDatasetRef`：通过指定质量规则的数据集引用。
- `ImageBatchRef`：图像批次引用。
- `LabelSet`：标签集合。
- `PredictionSet`：预测结果集合。
- `MetricSet`：评价指标集合。
- `PaperClaimSet`：经过结构化整理的论文主张。
- `Comparison`：比较结果。
- `ExperimentRecord`：实验记录。
- `ReportRef`：报告引用。
- `ArtifactRef`：通用产物引用。

后续根据学科需求扩展结构化类型。

类型校验不能只检查名称。例如，两份预测结果即使都属于 `PredictionSet`，也必须核对任务类型、样本标识、类别顺序和数据拆分版本，才能确定是否可以比较。

## 5.3 参数配置

节点参数必须具有明确的校验规则。

例如，医学评价节点可以配置：

- 评价指标。
- Bootstrap 次数。
- 置信区间计算方式。
- 标签处理规则。

参数校验需要同时发生在前端和后端。前端用于及时提示，后端负责最终判定。

工作流 JSON 不允许直接包含任意 Python 或 Shell 命令、任意文件系统路径或密钥。确需执行代码的科研节点必须通过受控执行环境调用，并具有单独的权限与资源限制。

# 第六章 工作流编辑器与用户体验

## 6.1 核心界面

主工作区采用节点式画布，配合节点目录、参数配置面板和运行监控面板。

建议使用 React Flow（`@xyflow/react`）实现画布交互；具体版本和许可情况在开发时确认。

界面主要包括：

1. **节点目录：** 按通用科研、医学科研、论文审查和控制节点分类。
2. **工作流画布：** 增删节点、连线、断线、移动、缩放、分组和查看连接关系。
3. **参数面板：** 配置当前节点的输入、算法参数和运行条件。
4. **校验面板：** 展示缺失输入、类型冲突、权限问题和依赖错误。
5. **运行面板：** 显示执行状态、耗时、日志、失败原因和资源消耗。
6. **产物面板：** 查看每个节点生成的数据、指标、图表、模型或报告。
7. **版本面板：** 比较不同版本的节点、连线和参数变化。

## 6.2 两种使用难度

### 简洁模式

普通科研人员从模板开始，系统只显示主要节点和必要参数。

用户可以直接修改模型、评价指标或数据源，不必理解整个底层架构。

### 专家模式

用户可以打开完整画布，增加节点、调整连接、构建分支、修改高级参数和复用子工作流。

两种模式使用同一套节点定义、工作流版本和执行引擎，不能分别维护两套互不兼容的流程系统。

## 6.3 必须避免的体验问题

- 画布可以连线，但无法保存。
- 保存后刷新，节点或连线丢失。
- 参数修改后没有影响真实执行。
- 节点失败只显示一个笼统的错误提示。
- 运行结束后无法查看各节点产物。
- Agent 生成的工作流无法在画布中打开。
- 复杂功能过多，导致新用户不知道从哪里开始。

核心体验应当是：用户可以从一个模板出发，理解每个节点的作用，修改工作流，运行并查看真实结果。

# 第七章 工作流引擎与运行机制

## 7.1 核心架构

工作流系统建议分为以下后端模块：

1. 工作流管理 API。
2. 节点注册表。
3. 工作流图校验器。
4. 工作流版本管理。
5. 执行计划生成器。
6. 工作流调度器。
7. 科研 Worker。
8. 产物存储。
9. 运行状态和事件日志。
10. 结果查询与报告服务。

前端画布负责编辑和呈现，后端负责验证和执行。不能将真正的科研运行逻辑只写在前端。

## 7.2 工作流执行流程

工作流执行需要经过以下逻辑环节：

**保存草稿 → 图结构校验 → 参数与数据校验 → 权限检查 → 运行审批 → 固定运行快照 → 调度执行 → 保存产物 → 汇总结果。**

这些环节是执行引擎内部的处理机制，不意味着用户必须在每次科研任务中手动经过固定数量的页面或阶段。

不同节点可以根据类型和权限采用不同的审批策略。

## 7.3 节点执行规则

- 只有上游依赖满足的节点才能进入可执行状态。
- 互不依赖的节点可以并行运行。
- 必需输入缺失时，节点不得启动。
- 质量门失败时，下游依赖该质量门输出的节点不得运行。
- 节点失败后，可以根据错误类型进行重试或进入修复流程。
- 每次运行都必须引用明确的工作流版本。
- 运行中的工作流不能因为用户继续编辑画布而悄然改变。

对于确定性节点，可以在输入产物、参数和执行器版本一致时复用缓存。训练等具有随机性的任务还需要记录随机种子、环境和模型权重版本。

## 7.4 状态管理

工作流运行状态建议包括：

`draft`、`pending_approval`、`queued`、`running`、`succeeded`、`failed`、`cancelled`。

节点状态建议包括：

`pending`、`running`、`succeeded`、`failed`、`blocked`、`skipped`。

对于需要人工操作的任务，还可以设置 `waiting_for_input` 或 `waiting_for_approval` 等状态。

所有状态都必须与真实的后端任务状态一致。

# 第八章 Agent 自动科研系统

## 8.1 Agent 的角色

Agent 是科研工作流的智能规划、配置、调度与分析层，不应取代工作流引擎。

工作流引擎负责确定性执行、状态管理和安全校验；Agent 负责处理目标理解、任务规划、工具选择、异常分析和下一步决策。

这种分工既能实现智能化，也能保证研究过程可检查。

## 8.2 Agent 的核心能力

### 能力一：理解研究目标

用户可以用自然语言描述研究任务。

例如：

“比较两个医学图像分类模型在同一验证集上的性能，检查数据泄漏风险，分析主要错误病例，并生成可追溯的评价报告。”

Agent 应将目标转化为明确的任务需求，包括输入数据、模型、评价指标、约束条件和最终产物。

### 能力二：检查资源和依赖

Agent 查询可用数据集、节点、模型和已有结果。

如果缺少必要数据、标签、模型权重或权限，应明确提出缺失项，而不是自行假设资源存在。

### 能力三：构建工作流

Agent 根据任务需求选择合适的节点，生成节点实例、参数和连接关系。

生成结果必须符合统一的工作流图结构，且可以被工作流服务校验。

### 能力四：执行和跟踪

在获得必要批准后，Agent 请求执行工作流，并持续读取真实运行状态。

它应能够区分排队、运行成功、运行失败和等待人工输入，不能将提交成功描述为科研任务已经完成。

### 能力五：结果解释与迭代

Agent 根据实际产物分析结果是否满足目标。

如果模型比较发现差异，Agent 可以进一步安排错误分析；如果质量检查失败，则可以提出数据修复方案；如果实验结果不足以支持研究主张，则应指出证据缺口。

后续任务必须建立在实际结果和可用资源之上。

## 8.3 Agent 的任务循环

Agent 内部可以采用以下循环：

**理解目标 → 规划任务 → 检查资源 → 构建或调整工作流 → 校验 → 获批执行 → 读取结果 → 评价与反思 → 决定下一步 → 生成报告。**

这只是 Agent 的内部协作机制，并不是限制科研任务的固定流程。

如果任务简单，Agent 可以只调用一个组件。如果任务复杂，它可以生成包含多个分支和子工作流的执行图。

## 8.4 工作流生成与审批

Agent 生成的图首先是草稿。

工作台应清楚显示：

- 新增了哪些节点。
- 建立了哪些连接。
- 修改了哪些参数。
- 每个节点的作用是什么。
- 需要哪些数据和权限。
- 预计有哪些产物。
- 哪些操作需要审批。

用户可以修改草稿、重新校验，再根据操作风险决定是否批准执行。

高资源消耗、外部数据提交、关键研究参数变更及实际实验操作应具有明确的权限和审批机制。

## 8.5 如何证明 Agent 真正实现了自动科研

不能仅以自然语言回答质量作为判断标准。

需要至少检查：

1. Agent 能否根据任务创建合法工作流。
2. 工作流能否在画布中打开和编辑。
3. 后端能否按图执行，而不是调用隐藏的固定流水线。
4. Agent 能否读取实际执行结果。
5. Agent 能否根据失败信息提出合理的修复方案。
6. Agent 能否根据真实结果创建下一轮任务。
7. 所有调用、审批、运行和产物是否可以追溯。

# 第九章 AgentArts 与自研平台的协作

## 9.1 职责划分

AgentArts 主要承担智能体的配置、推理、任务编排和工具调用。

自研科研平台负责：

- 工作流画布。
- 节点注册表。
- 工作流版本。
- 图结构校验。
- 运行调度。
- 科研数据和产物管理。
- 审批、权限和审计。
- 逐节点状态与报告。

AgentArts 不应成为科研数据、工作流版本和运行记录的唯一存储层。

## 9.2 交互机制

通过 MCP 或受控 API，将 AgentArts 与科研平台连接。

AgentArts 负责生成符合协议的工作流草稿，并调用查询、校验、提案和状态查询工具。

科研平台负责验证图结构和权限，决定是否允许执行，并保存实际运行记录。

## 9.3 建议的工具接口

| 工具 | 功能 |
|---|---|
| `get_project_overview` | 查询项目目标、数据和现有资源 |
| `list_node_types` | 查询可用节点及其输入输出 |
| `get_workflow_templates` | 查询可复用工作流模板 |
| `check_dataset_quality` | 运行或查询数据质量检查 |
| `validate_workflow` | 校验节点图、参数与依赖 |
| `create_workflow_draft` | 创建可编辑的工作流草稿 |
| `create_run_proposal` | 针对明确版本创建待审运行提案 |
| `get_workflow_run_status` | 查询运行状态及可用产物 |
| `get_artifact_metadata` | 查询产物类型、版本和来源 |

接口可以根据实际开发条件调整，但必须覆盖工作流生成、校验、执行提案和运行追踪。

## 9.4 安全边界

- MCP 工具不能绕过后端权限校验。
- Agent 不得直接提交任意 Python 或 Shell 命令。
- 运行提案必须关联具体的工作流版本和内容哈希。
- 用户批准后，后端仍须重新检查图版本、数据版本和权限。
- 过期、被修改或不合法的提案不得启动任务。
- 工具调用失败时，Agent 必须报告失败，不得伪造运行结果。

# 第十章 医学科研主场景

## 10.1 场景定位

比赛阶段优先完成一个医学 AI 科研场景，以证明节点系统、科研组件和 Agent 能够协同工作。

可选任务包括胸部 X 光多标签分类或眼底图像青光眼筛查，最终以团队已有数据、算力和比赛要求为准。

医学场景是重点落地应用，不应反过来限制平台只能处理医学科研。

## 10.2 基础节点包

建议先实现以下节点：

1. 数据集选择。
2. 标签读取。
3. 数据质量检查。
4. 患者级或样本级数据泄漏检查。
5. 图像预处理。
6. 模型加载或推理。
7. 模型训练。
8. 指标计算。
9. 模型比较。
10. 错误病例分析。
11. 可解释性结果展示。
12. 论文主张核查。
13. 结果报告生成。

每个节点都必须有明确的输入输出和真实执行结果。

## 10.3 复杂医学科研示范

建议将双模型比较作为首个复杂工作流示范。

用户从同一份数据出发，先执行质量检查和数据划分，再将数据分叉给两个模型。两个模型分别产生预测结果，随后进入独立评价节点，最后汇总指标、比较差异并生成报告。

其中任一模型失败时，另一个独立分支的结果仍应保留；比较节点需要等待其必需输入，或者按照明确的缺失结果策略处理。

后续可以增加参数搜索、交叉验证、错误分析和多轮优化。

## 10.4 医学场景的成果要求

最终产物应包括：

- 数据来源和质量报告。
- 实际运行的工作流版本。
- 模型配置和预测结果。
- 评价指标及必要的统计区间。
- 主要错误病例分析。
- 论文证据对比。
- 可追溯的研究报告。

所有结果都必须区分真实运行结果、预置演示结果和尚未完成的分析。

# 第十一章 论文复现与审查特色能力

## 11.1 产品定位

论文复现与审查属于通用科研能力，可以独立运行，也可以嵌入医学模型比较、实验分析或其他研究工作流。

其目标不是简单地生成论文摘要，而是把论文中的方法、实验条件和结论转化为可以逐项核查的研究对象。

## 11.2 组件能力

- 论文方法和研究主张提取。
- 数据、代码及补充材料登记。
- 实验条件整理。
- 指标口径核查。
- 统计结果复算。
- 可用代码的受控运行。
- 原论文与当前结果的差异分析。
- 证据充分性与限制说明。
- 复现或审查报告生成。

## 11.3 工作流集成方式

论文审查节点可以位于研究开始阶段，帮助检查相关方法和主张；也可以位于研究结果阶段，将当前结果与论文报告结果进行比较。

它不需要固定处于某个阶段，具体位置由研究目标和数据依赖决定。

## 11.4 证据分级

系统必须明确区分：

- 已从原始材料中提取的信息。
- 已完成的统计复算。
- 已实际执行的代码复现。
- 仅根据现有材料作出的解释。
- 因缺少数据、代码或条件而无法核查的内容。

没有原始数据或代码时，不应声称完成了实证复现；没有真实湿实验记录时，不应声称完成了物理实验。

# 第十二章 生物科研扩展示范

## 12.1 定位

生物科研用于展示通用科研底座可以迁移到其他学科。

首阶段不建设完整的生物科研平台，只选择少量具有代表性的节点，复用已有通用能力。

## 12.2 示例节点

- 菌株或样本记录读取。
- 培养条件导入。
- OD、pH 等数据读取。
- 实验数据质量检查。
- 趋势分析和统计绘图。
- 结果比较。
- 实验报告生成。

## 12.3 扩展验收

生物示范必须使用与医学场景相同的工作流引擎、节点协议、产物存储和运行记录机制。

它的价值是证明平台可以通过增加专业节点扩展研究场景，而不是另行开发一套独立系统。

# 第十三章 科研项目、版本和证据追溯

## 13.1 项目数据模型

每个科研项目至少需要关联：

- 研究目标。
- 数据集与数据版本。
- 论文和证据。
- 工作流及其版本。
- 节点运行记录。
- 模型与实验配置。
- 运行产物。
- 研究结论和报告。

项目状态不是单纯的任务进度条，而是研究资源和研究结果之间的关系记录。

## 13.2 运行记录

每次工作流运行需要记录：

- 工作流版本和内容哈希。
- 使用的数据版本。
- 节点类型及其版本。
- 参数快照。
- 执行时间和状态。
- 输入产物与输出产物。
- 执行器版本。
- 错误码及日志。
- 操作者和审批记录。

## 13.3 可复现要求

用户应能够重新打开历史工作流，查看当时的配置和结果。

对于具备重跑条件的任务，应允许使用固定版本重新执行，并比较新旧结果。

如果依赖的数据、模型或外部服务已经变化，系统必须明确标记，不应将重新运行描述为与原运行完全相同。

# 第十四章 数据安全与执行安全

## 14.1 数据访问

所有数据引用都必须经过服务端权限检查。

工作流图中保存的是数据或产物引用，不应直接嵌入大型影像、模型文件或敏感数据内容。

## 14.2 执行隔离

科研 Worker 只执行注册表中允许调用的执行器。

对于确需运行用户代码的场景，必须使用独立、受限的执行环境，并限制网络访问、文件访问、运行时间和资源消耗。

## 14.3 运行审批

审批策略应根据操作风险确定。

低风险的只读分析可以采用较轻的审批方式；高资源消耗任务、关键研究参数修改和外部操作应使用更严格的确认机制。

## 14.4 审计与恢复

系统应保留运行日志、审批记录和产物引用。

发生失败时，应能够定位失败节点，保留已完成分支的结果，并支持在符合条件时重试。

# 第十六章 技术架构与实现建议

## 16.1 前端

采用 React 与 React Flow 构建节点画布。

前端重点实现：

- 节点和端口渲染。
- 拖拽和连线。
- 参数编辑。
- 图结构校验提示。
- 版本保存。
- 运行状态展示。
- 产物预览。

前端只负责编辑和展示，不负责决定最终的执行权限或执行顺序。

## 16.2 后端

可沿用团队现有 Python 技术基础，以 FastAPI 提供工作流、节点、运行和产物 API。

后端重点实现：

- 节点注册与类型定义。
- 工作流图保存和验证。
- 执行计划生成。
- 任务调度和状态管理。
- 科研 Worker 调用。
- 运行日志与产物索引。
- 权限与审批。
- AgentArts 接口。

具体数据库和任务队列的选型应根据部署环境、并发需求和现有代码决定，不应为了架构复杂度而提前引入不必要的中间件。

## 16.3 存储

结构化数据用于保存项目、节点定义、工作流版本、运行状态和产物元数据。

大型文件、模型权重、图表和报告通过受控文件或对象存储保存，数据库只记录引用和必要的元数据。

## 16.4 AgentArts 接入

通过 MCP 或 API 调用受控的科研工具。

AgentArts 内部的智能体工作流与用户可编辑的科研工作流需要明确区分：

- 前者负责智能体内部推理与工具调用。
- 后者负责用户科研任务的节点编排与实际执行。

两者可以协作，但必须使用一致的工作流协议和项目标识。

# 第十八章 开发阶段与里程碑

原计划中的 W0–W3 已经过期，因此后续按工程里程碑推进，不再沿用已经失效的日历安排。具体日期由团队根据比赛截止时间和当前代码状态确定。

## 阶段 A：工作流协议与最小画布

目标：证明平台能够保存一张真实可编辑的节点图。

任务：

1. 定义节点和端口协议。
2. 定义工作流 JSON。
3. 实现三个简单的测试节点。
4. 实现拖拽、连线和断线。
5. 实现保存、加载和版本恢复。
6. 实现基本服务端校验。

验收：刷新页面后图结构保持一致；非法连线被识别；工作流版本可以恢复。

## 阶段 B：真实按图执行

目标：证明画布不是静态展示。

任务：

1. 实现图校验器。
2. 实现依赖分析和执行计划。
3. 实现节点调度。
4. 实现节点状态和运行记录。
5. 实现产物保存和查看。
6. 实现失败节点定位。

验收：修改一条合法连线后，真实执行路径或结果发生相应变化；每个节点都能查看运行状态与产物。

## 阶段 C：医学科研主闭环

目标：形成完整且可追溯的医学科研演示。

任务：

1. 实现数据集选择和质量检查。
2. 实现医学图像预处理或模型输入准备。
3. 接入至少两个可比较的模型实例或模型配置。
4. 实现模型评价。
5. 实现结果比较。
6. 实现报告生成。

验收：一份固定的演示数据能够通过实际运行得到质量报告、评价结果和最终报告。

## 阶段 D：AgentArts 工作流生成

目标：让 Agent 根据科研目标创建真正可执行的工作流草稿。

任务：

1. 暴露节点目录查询工具。
2. 暴露工作流模板查询工具。
3. 暴露工作流校验工具。
4. 暴露工作流草稿创建工具。
5. 暴露运行状态查询工具。
6. 实现草稿编辑、审批和后端复核。

验收：Agent 生成的工作流能够打开、修改、校验和运行；无效草稿无法启动执行。

## 阶段 E：特色能力与稳定性

目标：完成论文证据核查、异常恢复和答辩准备。

任务：

1. 实现论文主张与证据核查。
2. 实现结果比较与报告追溯。
3. 测试非法参数、错误连接和运行失败。
4. 测试版本变更与审批失效。
5. 完成部署、操作说明和演示录制。
6. 有余量时增加生物扩展示范。

验收：整个演示从项目启动到结果报告可重复运行，并且所有关键结果都有对应的运行记录。

# 第十九章 项目验收标准

## 19.1 节点编辑验收

- 可以添加、删除和移动节点。
- 可以连接和断开端口。
- 可以配置参数。
- 可以保存并恢复工作流。
- 可以创建不同版本。
- 可以识别缺失输入和不兼容类型。

## 19.2 执行引擎验收

- 后端根据保存的图生成实际执行计划。
- 节点按依赖关系执行。
- 独立分支可以并行运行。
- 失败节点会阻断依赖它的下游任务。
- 运行记录关联明确的工作流快照。
- 可以查看各节点输入、输出和错误原因。

## 19.3 Agent 验收

- Agent 能够查询节点能力。
- Agent 能够生成结构化工作流草稿。
- 工作流草稿能够在画布中打开。
- Agent 能够读取真实运行状态。
- Agent 能够基于实际失败信息提出修正方案。
- Agent 不得伪造未执行的科研结果。

## 19.4 科研结果验收

- 数据质量报告来自真实运行。
- 模型指标由实际预测结果计算。
- 论文比较具有明确的证据来源。
- 报告可以追溯到数据、模型和运行版本。
- 结果不足时能够明确标记不确定性与限制。

## 19.5 用户体验验收

邀请一名未参与核心开发的队员完成以下操作：

1. 打开医学科研模板。
2. 增加一个模型分支。
3. 配置并保存工作流。
4. 运行工作流。
5. 查看评价结果。
6. 定位并处理一个预设错误。
7. 打开最终报告并追溯结果。

如果用户只能在开发人员指导下完成这些操作，说明界面和交互仍需要优化。

# 第二十章 风险与应对

## 风险一：画布完成，但后端仍然是固定流水线

**应对：** 在开发最早期就实现最小图执行器，以实际修改连线改变执行路径作为阶段验收条件。

## 风险二：Agent 只能输出文字，不能创建工作流

**应对：** 统一 Agent 与画布使用的工作流数据协议，先实现结构化草稿创建，再逐步增加智能规划能力。

## 风险三：功能太多，导致比赛版本无法完成

**应对：** 以 P0 为硬性范围，优先完成节点图、执行器、医学闭环和 AgentArts 接入；复杂控制结构按阶段增加。

## 风险四：论文审查被误认为真正的论文复现

**应对：** 分开记录文献提取、统计复算、代码复现和实际实验状态，明确每项证据的可核查范围。

## 风险五：复杂工作流导致执行不可控

**应对：** 设置循环上限、超时、资源预算、权限检查和失败恢复机制。所有执行都必须经过服务端校验。

## 风险六：演示依赖预置结果，无法证明真实能力

**应对：** 固定演示数据与预期结果，现场执行至少一个真实节点；同时保留完整运行记录，并准确区分预运行结果和现场执行结果。

# 第二十一章 最终产品形态

最终产品应提供三种相互衔接的使用方式。

**直接使用组件：** 用户选择一个科研功能，提供输入并获得结果。

**可视化工作流：** 用户自由编排节点，搭建适合当前研究任务的执行图。

**Agent 驱动科研：** 用户描述研究目标，由 Agent 生成、校验和调整工作流，并在获得必要授权后执行，随后根据结果推进后续研究。

三种方式使用同一套科研组件、工作流协议、执行引擎和产物管理机制。

工作流模板负责降低使用门槛，专业组件负责扩展学科能力，Agent 负责提高规划和执行效率。

它们都不应限制用户构建复杂科研场景的能力。

## 项目最终目标

建设一个真正能够将科研目标转化为可执行任务、将科研工具组合成复杂工作流、将执行结果转化为可追溯证据的智能科研平台。

比赛阶段以医学科研闭环证明系统有效，以论文复现与审查展示科研可靠性，以生物组件展示跨学科扩展能力。

更长期的目标是让科研人员能够从一个简单任务开始，逐步构建更复杂的研究场景，并让 Agent 在明确的权限、数据和证据约束下，持续协助推进科研工作。
